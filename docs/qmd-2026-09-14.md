# qmd: local search over the notes that matter — 2026-09-14

[tobi/qmd](https://github.com/tobi/qmd) is a hybrid document search engine
for one machine: BM25 over SQLite FTS5, vectors, an LLM reranker, all in
`~/.cache/qmd/index.sqlite`. It went in today as the "local documents"
capability of the launcher's AI Chat
(docs/vicinae-ai-extensibility-2026-09-14.md §2.4), and turned out to have a
better corpus waiting than the one it was planned for. By evening the stock
local GGUF models had proved unusable on this GPU-less machine and the
installed qmd became a fork whose models are pxy's (§4).

## What landed

- **`home/dot_config/qmd/index.yml`** — qmd's whole configuration,
  chezmoi-managed: four collections and the model choices. qmd rewrites it
  itself on `qmd collection add` / `qmd context add`, through the symlink,
  so a change made on one machine is a repo change to commit.
- **`run_after_56-qmd.sh`** — builds and installs the fork
  (saifulapm/qmd, branch `remote-models`, §4) as an npm global under the
  mise node, with run_after_04's guard against the stale-shim trap.
- **`qmd-refresh.timer` / `.service`** — hourly `qmd update` and `embed`,
  enabled by run_after_02. The service is the only place indexing happens;
  an apply never waits for it.
- **`ai-ask-mcp.json`** — the `qmd` entry is on. The chat spawns `qmd mcp`
  over stdio the first time a message is sent and asks it for `query`, `get`,
  `multi_get` and `status`.

## 1. The collections, and why these

| collection | path | files | why |
| --- | --- | --- | --- |
| `dotfiles-docs` | `~/.dotfiles/docs` | 22 | the notes like this one: what was built and why |
| `mem` | `~/.local/share/mem/store` | 8,150 | the system of record for AI sessions: 934 facts, 803 rulings, 569 handoffs, ~400 questions and answers, 5,182 log lines, and every project's wiki, plan, roadmap, status |
| `project-docs` | `~/Sites` | 265 | each repo's README, CLAUDE.md, HANDOFF.md and docs/ tree |
| `dotfiles` | `~/.dotfiles` | 402 | the repo as code: scripts, units, fish, QML, extension sources — **excluded from unscoped queries** |

`mem` is the one that matters. `mem search` already exists and is full-text;
what qmd adds is finding a ruling worded differently from the question, and
the reranker choosing between the five rulings that match. The records are
TOML-fronted (`+++`), which qmd does not parse, so the ULID is the title and
the header text (kind, project, machine, date) is part of what is searched —
`kind = "ruling" splitroute` is a working query.

`project-docs` was `**/README.md` first and indexed 1,817 files, most of them
READMEs of code vendored under `omniroute/references` and `kojev-tv`. `~/Sites`
is exactly two levels deep (github/<repo>, tries/<repo>, laravel/<app>), so
`*/*/README.md` and `*/*/docs/**/*.md` take a repo's own prose and nothing
below it.

`dotfiles` has `includeByDefault: false`: a question about a design decision
should not drown in config lines. It is there for "where is X configured",
scoped in with `-c dotfiles` or the MCP `collections` parameter.

**Not a collection: Claude Code's memory files.** They were in the first
draft (47 short, curated facts under `~/.claude/projects/*/memory`); Saiful
is turning that memory off, so they are out.

Every collection has a `context` string. qmd returns it beside each hit and
its README calls that the feature that lets a model choose the right
document. Keep them accurate when a collection changes.

## 2. How to use it

**From a shell.** Three verbs, in order of cost:

```sh
qmd search "AVRCP wedge"            # BM25 only, instant, exact words
qmd vsearch "the headset that hangs"  # vectors only, paraphrase
qmd query "why does the homepod sink live in its own unit"   # hybrid + rerank
qmd query "…" -c mem -n 10 --json   # scoped, structured
qmd get "qmd://dotfiles-docs/yazi-2026-08-18.md"
```

`query` runs the embedding, reranker and query-expansion models, so the first
call after a reboot pays a model load. Everything reports `docid`, `score`,
`file`, `title`, `context`, `snippet` with `--json`.

**From the launcher.** AI Chat with the Tools preference on: ask, and the
model calls `qmd: query` when the question sounds like it is about your own
records, then `qmd: get` on the hits it wants to read. **Verified**: "which
engine option was chosen for splitroute, and when?" ran one lex+vec query
(1.8 s), three gets, and answered "Option B, decided 2026-09-02", which is
what the mem ruling says. Three things had to be true first, all in
`ai-ask-mcp.json` and `capabilities/mcp.ts`:

- The server entry's `description` names the collections. With the local
  models it also had to tell the model to use `searches` (one lex, one vec)
  with `rerank: false`: left to itself nemotron invented a collection called
  "notes", sent the plain `query` string (which ran the 1.7 B expansion
  model) and asked for reranking — and timed out. Since §4 the hint says the
  opposite: prefer the plain `query`, expansion and rerank are seconds.
- The MCP call timeout is five minutes, not the SDK's 60 s.
- `get` answers with an embedded `resource` block, not text; the client
  reads `resource.text`. Before that fix every get came back as
  "(resource content)" and the model gave up.

**Keeping it fresh** is the timer's job: `systemctl --user list-timers
qmd-refresh.timer` shows the next run, `journalctl --user -u qmd-refresh`
what the last one did. After adding a collection, `qmd update` then
`systemctl --user start qmd-refresh.service` rather than waiting an hour.

## 3. Hard-won

- **npm 11 skips the native postinstalls.** `npm install -g @tobilu/qmd`
  warns that node-llama-cpp and five tree-sitter grammars have install
  scripts "not yet covered by allowScripts" and does not run them. qmd works
  anyway: node-llama-cpp fetches a CPU build at first use and the grammars
  ship prebuilds. Verified: index, search, embed and doctor all ran. No
  `--allow-scripts` in the install script for that reason.
- **CPU embedding is slow on this machine.** `qmd doctor`: "running on CPU
  (10 math cores)", no Vulkan. 22 docs / 211 chunks took 4 m 19 s, about a
  second a chunk. The mem store's ~10,000 chunks are hours of CPU; qmd caps
  each `embed` session at 30 minutes and keeps what it finished, so the
  hourly timer works the backlog off in slices (1,670 vectors after the
  first), and indexing is never part of an apply. Later runs embed only
  what changed.
- **Reranking is not interactive here.** `qmd query … -c mem` with the
  reranker took 7 m 36 s of wall time (26 CPU-minutes) while the embed
  service was running; `qmd search` took 0.2 s and a lex+vec MCP query
  1.8 s. Hence the hint above: no rerank, no expansion, from the chat.
- **Vulkan: no binary.** `QMD_LLAMA_GPU=vulkan qmd doctor` reports
  `NoBinaryFoundError` and falls back to CPU — node-llama-cpp ships no
  Vulkan prebuild for linux-arm64. A source build against Asahi's
  honeykrisp driver is the untested way to a GPU.
- **Why not pxy's models instead of local ones** (asked today): qmd 2.8.3
  cannot. `dist/llm.d.ts` declares an abstract `LLM` interface (embed,
  generate, expandQuery, rerank), but the store and CLI only ever construct
  `LlamaCpp`, `StoreOptions.llm` is typed as that class, and the store's
  sessions are written around it. pxy is ready on its side — `/v1/rerank`
  answers via jina, `/v1/embeddings` via `text-embedding-v4` (1024 dims) —
  so an `OpenAiLLM` backend inside qmd, selected from `index.yml`, is the
  real fix for a GPU-less machine: no model downloads, embeds and reranks
  in seconds. Built the same evening as a fork — §4.
- **`qmd pull` before `qmd query`** (local models only, historical). The
  reranker (640 MB) and query expansion (1.1 GB) models downloaded on first
  use otherwise, in the middle of the first question; the service pulled
  them. With pxy's models there is nothing to pull.
- **The MCP server lives as long as the chat view.** With
  `pop_to_root_on_close` false, Escape suspends the chat; `qmd mcp` and its
  loaded models stay warm across Alt+Space and exit when the stack is popped.

## 4. The fork: pxy's models instead of local GGUF (same day, evening)

The "why not pxy" bullet above became the work. `~/Sites/github/qmd` is a
fork of tobi/qmd (origin `saifulapm/qmd`), branch **`remote-models`**, one
commit on top of upstream `main` (v2.8.3 + #949): an `OpenAiLLM` backend
behind the `LLM` interface qmd already declared but never let anything
implement. Opened upstream as [tobi/qmd#954](https://github.com/tobi/qmd/pull/954)
(2026-09-14). Upstream has seven unmerged attempts (#517, #619,
#629, #705, #720, #761, #769, tracking issue #620); all conflict with today's
`main`, the closest in shape (#619) is 233 commits behind, and the only
maintainer guidance (on #517: include query expansion, unit-test the remote
calls with mocked HTTP) is what this one follows.

**How it is selected.** Model URIs pick the backend the way `hf:` already
did: `openai:<model id>` for all three roles, plus the endpoint. The
`models:` block of index.yml is now

```yaml
models:
  embed: openai:text-embedding-v4        # DashScope, 1024-d, batches of 10
  generate: openai:general               # pxy chat group, for query expansion
  rerank: openai:auto                    # pxy's rerank chain (voyage, jina)
  openai_base_url: http://127.0.0.1:4100/v1
  openai_api_key: pxy-local              # QMD_OPENAI_API_KEY would override
  openai_generate_params:
    reasoning_effort: none
```

The last key exists because nemotron (the `general` group's first member)
spends the whole 600-token budget reasoning and returns an empty `content`;
with `reasoning_effort: none` it answers the expansion prompt in 1.1 s.
Vectors are stored under the `openai:` URI, so the switch was an ordinary
model change: the first `qmd embed` after it refused to mix the 1,670 old
768-d vectors with 1024-d ones ("dimension mismatch, run `qmd embed -f`"),
which is exactly what `embed -f` then did. `qmd pull` says there is nothing
to download; `qmd doctor` probes `GET /models` instead of the GPU and no
longer prints the CPU warning; `qmd status` shows the endpoint.

**What changed in the fork** (513 lines added, 92 removed, nine files):
`src/llm.ts` gains `OpenAiLLM`, `createLlm()` and a shared
`parseExpansionLines`; the `LLM` interface gains `embedBatch`, the model-name
getters and *optional* `tokenize`/`detokenize`, so `store.ts` chunks by
character estimate when the backend has no tokenizer; store, sessions, CLI
and `createStore` are typed to `LLM`; `collections.ts` knows the three
`openai_*` keys; `trust.ts` adds `openai_base_url` to the digest of a
project-local config, because it decides where documents are sent.
`test/llm-openai.test.ts` (11 tests, stubbed `fetch`) covers request shapes,
batching, errors, key precedence, expansion parsing and rerank mapping; the
whole vitest suite passes (1,257 tests), the Bun leg of `npm test` was not
run (no bun here).

**Timings, before → after, same machine, same corpus:**

| operation | local GGUF on CPU | pxy |
| --- | --- | --- |
| embed dotfiles-docs (22 docs, ~210 chunks) | 4 m 19 s | 7 s |
| embed everything (8,858 docs, 12,280 chunks) | hours, in 30-min slices | 5 m 13 s |
| `qmd query … -c mem` with expansion + rerank | 7 m 36 s | 3.4 s |

**Install.** `npm install -g github:saifulapm/qmd#remote-models` does not
work: the package's `prepare` hook builds with tsc and a git install never
gets the typescript peer (MODULE_NOT_FOUND, verified). run_after_56 clones
the branch into `~/.local/share/qmd/src`, runs `npm install`, builds, packs
and installs the tarball; it compares the commit `qmd --version` reports
with the clone's HEAD, so a re-run is a fetch and nothing else, and a
machine offline builds what it has. 38 s on this machine.
`~/.cache/qmd/models` (2.2 GB of GGUF) was unused after the switch and was
deleted.

**The retrieval caveat found while verifying.** The note above says the chat
answered "Option B, decided 2026-09-02" to "which engine option was chosen
for splitroute". That record (`global/items/…31N9QEMA`) is a global fact
about the *Dactyl* engine and never mentions splitroute; the old lex+vec
query hit it on "engine option" alone. With reranking on, the same question
now ranks splitroute's own records first and the Dactyl fact drops out of
the top ten, which is the reranker doing its job. Asked without the wrong
project — "which engine option was chosen, and when?" — it is hit one at
92%.

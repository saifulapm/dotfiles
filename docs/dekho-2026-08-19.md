# A Movies & TV hub in the shell, on top of dekho — 2026-08-19

User ask: make a Quickshell overlay panel around
[dekho](https://github.com/saifulapm/dekho) — a beautiful hub that plays,
resumes and explores; change dekho itself where it needs changing; wire it into
the dotfiles so every machine has it; and don't cost the shell any performance.

Bound at **Mod+Ctrl+Alt+M**, `qs ipc call dekho toggle`, and Menu > Movies & TV.

---

## 1. What dekho could not do yet

dekho was a good terminal program and a useless library. Every entry point was
an `inquire` picker on a TTY, the only machine-readable output was
`browse --list` (two columns of text), `SearchHit` dropped `poster_path` on the
floor, and nothing anywhere remembered that you were 40 minutes into a film. A
panel cannot be built on that, so dekho grew five things — implemented in a
background `claude --bg` session against a written contract, while the QML was
built against the same contract at the same time:

| Added | Why the panel needs it |
|---|---|
| `dekho api {search,trending,discover,genres,languages,title,episodes,history,prefetch}` | one JSON object per call on stdout, diagnostics on stderr — the panel parses stdout blind |
| poster/backdrop/overview on every result | there is no hub without art |
| `dekho api prefetch --size w342 <paths…>` | downloads TMDB images into `~/.cache/dekho/img/<size>/` and answers with the directory |
| watch history in `~/.local/state/dekho/history.json` | Continue watching, and the Resume button |
| `dekho play --id … --kind … [--resume] [--json]` | non-interactive playback that narrates itself as NDJSON |

**No new crates.** dekho already hand-rolls `urlencode` with a comment saying
the dependency list is what was approved; the config parser below follows that
rather than pulling in a TOML crate for one key.

Everything is still a good terminal program: `dekho api trending | jq`,
`dekho play --id 550 --kind movie` and `dekho --resume breaking bad` all work
from a shell, and the interactive pickers are untouched.

## 2. The shell holds no key and speaks no HTTP

The panel spawns `dekho api` and reads stdout. That was a choice against the
obvious alternative — QML talking to TMDB directly — and it buys three things:
the TMDB key never enters the shell process, TLS and JSON parsing never run on
the shell's event loop, and there is exactly one implementation of "what is
trending" instead of two that can disagree.

Four `dekho api` calls fire per open (history, trending, movies, series), each
followed by a `prefetch` for its posters. Nine short-lived processes per open,
zero while closed.

## 3. Playback is not the shell's child

**This is the one thing in the change that would have been a bug if done the
obvious way.** Quickshell's `execDetached` children do not leave the shell's
cgroup — `systemd-cgls --user-unit qshell.service` lists every helper it spawns
— and `qshell.service` is `KillMode=control-group`. A `dekho play` started that
way dies with its mpv every time the shell restarts: the menu's Relaunch row, a
`chezmoi apply` that touches QML, a crash. bin/qshell-relaunch documents the
same trap from the other side.

So `bin/dekho-play` starts playback as a **transient systemd user unit**.
Measured on the desk:

```
dekho-play unit → /user.slice/…/user@1000.service/app.slice/dekho-play.service
qshell.service  → /user.slice/…/user@1000.service/session.slice/qshell.service
```

Different slices: restarting the shell cannot touch a film in progress. The
unit is `--collect`, so it retires itself when the film ends, and stopping it
stops mpv with it (mpv is dekho's child, same cgroup) — which is what the
panel's Stop button means.

**The session file is named by the panel, not by the wrapper.** `dekho play
--json` writes NDJSON to a file under `$XDG_RUNTIME_DIR/dekho/` and the panel
follows it with `tail -n +1 -F`. With one fixed filename that races: the panel
starts its tail the instant it spawns the wrapper, while the wrapper still has
to stop the previous unit before systemd truncates anything — so `tail -n +1`
replays the *previous* run's events into the new run's view. A path that has
never existed cannot be stale, and `-F` waits for it to appear.

## 4. What it costs when you are not using it

Nothing, and that is enforced structurally rather than by care:

- The surface is a `SurfaceLoader` marked `evictable` — nothing exists until
  the first summon, and the whole tree (with its decoded pixmaps) is released
  after the grace period. Idle RSS returns to where it was.
- **No polling, no timers, no service.** There is no `Services/Dekho.qml`; the
  module owns its own requests and they only run while it is open. The one
  long-running child is the `tail -F`, and `hide()` stops it.
- Every `dekho api` child runs under `setpriv --pdeathsig TERM` so a shell that
  dies cannot leave one holding a TMDB connection. Playback deliberately does
  not (§3).
- Posters decode at tile width via `sourceSize`, not at TMDB's 342x513 — about
  10 MB of pixmaps for a sixty-poster hub instead of 40.

`bench:first-bar` is unchanged (170–210 ms across the relaunches in this
session): none of this is on the startup path.

## 5. Two Qt decisions worth keeping

**Posters are not clipped to their radius.** Rounding a picture in Qt costs a
framebuffer per instance however it is done — `ClippingRectangle` is a
`layer.enabled` Rectangle plus a `ShaderEffectSource` (read
`/usr/lib64/qt6/qml/Quickshell/Widgets/ClippingRectangle.qml`), and
`layer.effect` is the same trade — and a hub draws sixty at once. Instead the
frame is a plain Rectangle stroked *over* the image on the rounded path: at
radius 4 on a ~150 px poster the nub left outside the stroke is about a pixel
at four corners. Invisible, and one ordinary rectangle node.

**The rail model is keyed, not built.** The first version computed an array of
row objects from eight properties that land at eight different moments (four
listings, four prefetches), so every arrival replaced the whole model and Qt
tore down and re-incubated every delegate — visible in the journal as
`Object or context destroyed during incubation`. Keyed on `["trending",
"movies", "tv"]` with per-rail lookup functions, the model changes once per
open and each rail updates when its own data lands.

## 6. Two bugs the live session found

Both were caught by driving the real panel, not by reading the code.

**The panel stopped answering the keyboard after one hide/show.** The layer
surface's `WlrKeyboardFocus.Exclusive` grab and the QML scene's active focus
are different things: a `hide()`/`show()` pair drops the grab to `None` and
back, and the item that had focus does not get it again by itself. The panel
held the entire keyboard and responded to nothing — `qs ipc call dekho search`
worked, typing did not. `OverlaySurface`'s header calls this out and
`Clipboard.qml` hit it first; `show()` now re-takes focus unconditionally.

**The backdrop was fetched from the filesystem root.** The poster (w342) and
the backdrop (w780) are two different prefetch calls into two different cache
directories, and they land independently. Guarding the path on the ready flag
alone let a poster that arrived first build the backdrop's path against an
empty directory: `Cannot open: file:///pF0qkRsrHkdYadPWY9AMeFZfcwk.jpg`. Both
paths now guard on the directory itself.

## 7. The TMDB key on three machines

`home/.chezmoitemplates/dekho.toml.age` → `~/.config/dekho/config.toml` (0600,
dir 0700), decrypted on every apply — the same mechanism and the same
`stat key.txt` guard as `mail-identities.toml`, so a phase-1 install with no
age key yet renders nothing, chezmoi removes the empty file, and dekho treats a
missing config as "no key here" rather than as an error.

`pass` was the alternative and was rejected: the store needs the gpg agent
unlocked, so the hub would fail on every boot until something else had unlocked
it — and the panel is exactly the kind of thing you open first.

dekho reads `$TMDB_API_KEY` first and only then the config file, so a terminal
keeps overriding it. The config parser is hand-rolled (§1): comments, blank
lines, `key = "value"`, one layer of quotes, unknown keys ignored.

## 8. Install

`run_after_42-dekho.sh` clones `github.com/saifulapm/dekho` into
`~/.local/src/dekho` and builds it into `~/.local/bin/dekho`, guarded on the
binary — **the first build is minutes**, because dekho links librqbit.
`update-all`'s `update_src` advances the checkout and drops the binary only
when origin actually moved.

`~/.local/src`, not `~/Sites/github/dekho`: the Sites copy is the development
checkout and may sit mid-change on an unpushed branch. Every machine runs the
same pushed revision, and this box is not special.

## 9. Deliberately not done

- **No bar widget.** The user picked keybind + menu row. A permanent bar entry
  would have meant either a dead button or something watching the history file
  to decide whether to show a dot, and neither earns a slot.
- **No `Services/Dekho.qml`.** Nothing about films needs to exist while the
  panel is closed — see §4. Media keys already reach mpv through the existing
  MPRIS layer with no special-casing.
- **No genre chips.** Sort chips (Popular / Top rated / Newest) apply to both
  catalog rails and re-query in place. Genres are kind-specific in TMDB
  ("Action" for films, "Action & Adventure" for series), so one shared chip row
  would have quietly emptied one of the two rails.

## 10. The redesign — same evening

The first design shipped working and looked like what it was: a settings
panel that happened to contain posters. The user's verdict — "Design looks
very bad. fonts very small, cards spacing, single view design etc. Can we
make something like Apple TV" — and the redesign that answered it kept every
constraint above (keyed rails, no per-card framebuffers, sourceSize on every
Image, nothing alive while closed) while replacing the whole presentation.

**Fullscreen, and opaque.** The 80% centred card read as a dialog about
films. The surface is now the whole screen, opaque `surface0`, with
`blurable: false` — a cinema is a room with the lights off, backdrop art over
wallpaper bleed looked like neither, and an opaque card skips what would have
been a fullscreen CardFrost FBO.

**A hero that follows the focus.** The top 52% of the screen is the focused
title's backdrop, edge to edge, with the title, meta line and overview over
two gradient scrims (one node each; a blur is a framebuffer). Backdrops are
fetched ONE per settled focus — `prefetch --size w780`, debounced 180 ms —
not as a fifth batch per rail: sixty w780 stills is megabytes of TMDB traffic
for art mostly never looked at, and dekho's disk cache makes every revisit
free. Two stacked Images crossfade so skimming a rail never flashes bare
surface; the outgoing art moves to the back plate as the same cached file, so
the handoff decodes nothing. w780 upscaled ~4.5x on the desk is fine behind
the scrims — `original` was rejected because a focus step would then cost a
3–8 MB download.

**A module-local type scale.** StyledText's roles stop at `Display` (18 px at
the default token) because they were measured off the bar and panels, and
raising `font.size` or adding roles would restyle the whole desktop. The hub
declares its own named steps (`fonts.hero` … `fonts.hint`) as `fontPx()`
multipliers — so a theme's font.size still scales them — times a boost
derived from screen height (clamped 1–2.1): 73 px hero type on the desk,
~40 px on a laptop panel. Same rule for geometry: edge padding is 3.2% of
width, poster width is the tighter of a width budget (~6.3 cards, one
bleeding off the right edge to say "this shelf continues") and a height
budget (the next rail's caption must stay visible under the hero), floored.

**tvOS focus, and the bugs it brought.** On focus the artwork zooms inside a
fixed frame — a transform scale on the Image (same nodes, new matrix — free,
where a glow effect on sixty cards would be sixty framebuffers), scissor-
clipped only while actually zoomed so the other ~59 cards never pay the
batch break. The first version scaled the whole card, which bulged the frame
over its neighbours and the rail caption; the user called it out. The bigger
corner radius broke §5's stroke-over rounding too: the uncovered nub outside
the arc grows with the radius — ~1 px at the original radius 4, ~4 px of
bright poster past the focus ring at the new radius 10. The cover is now an
oversized stroke in the page colour (outer radius 2r, width r+hairline) whose
inner edge lands exactly on the art's rounded path — still one rectangle node
per tile, possible only because the hub's page is opaque surface0; the detail
stills and playback poster sit on backdrop gradients where that cover cannot
work, so they keep radius 4 and the measured-invisible nub. The focused card
takes the accent ring and only then shows its label; at rest the art is the
label. Pointer and keyboard share one
cursor so the hero always describes the lit card — and driving that live
found the classic hover-steal: every Down scrolled a new card under the
parked pointer, whose hover re-fired and handed the focus straight back.
FilePicker had already solved it (compare the hover's *scene* position — a
card sliding under a stationary mouse re-fires with the same one), and the
guard is copied here for rails, grid and episode rows. The per-card rating
pills went too: the hero's meta line already rates the focused title, and
sixty pills were the old design's clutter in miniature.

**Detail and playback went full-bleed.** The detail page is the backdrop
edge to edge, hero-scale title, a filled accent Play pill, and episode rows
with real 16:9 stills — the `episodes` verb already carried `still` paths
and the generic `prefetch` fetches them at w342, so this cost dekho nothing.
The rows are capped at 62% width: stretched across the full 3266 px content
width, the runtime column sat a metre from the text it belongs to. The
playback view keeps the film's backdrop dimmed to 0.22 under the narration,
and driving it live found `"Buffering  at "` — the swarm's first ticks carry
zero bytes at zero rate, which formatBytes/formatBps collapse to "".

**What it cost: nothing measurable.** Cold start 211 ms / idle RSS 308 MiB /
idle CPU 0.45% against the pre-redesign 235 ms / 307 MiB / 0.55% — within
run-to-run noise, because nothing new runs while the panel is closed and the
hero is two Image nodes. The two `destroyed during incubation` lines that
appear when the evicted surface tears down mid-decode predate the redesign
(same pair, old line numbers, 17:52 in the same day's journal) and are the
eviction working as designed, not the §5 storm coming back.

## 11. Depth: a person, a browse screen, and a back stack — 2026-08-20

The redesign made the hub a place. It could not answer any question about what
was in it. The ask: *"Can we add more details on single view like Casts, more
details about this movie or series, trailer (via yt-dl to mpv) etc. also Movie
browse feature by filters and if i click any cast, genre, I should get filtered
by that."*

dekho grew the data for it in a parallel `claude --bg` session against a written
contract, the same way §1's verbs were built: `title` gained `tagline`, `status`,
`homepage`, `trailer`, `cast[]`, `crew[]`, `studios[]`, `countries[]`,
`languages[]`, `similar[]` and the per-kind numbers; `videos`, `person` and a
`trailer` verb appeared; `discover` gained `--cast` and `--year`. The QML below
was written against the contract before any of it existed and needed no change
when it landed — which is the second time that has worked and is now the way to
do this.

### Navigation is a stack, and that was the load-bearing change

`view` was a string with three values, and Escape meant "go to the hub". That is
the same thing as "go back" only while every screen is one step from the hub. It
stops being true immediately: a cast face opens a person, a person's credit
opens a title, that title's genre opens Browse, Browse opens another title. Four
screens in there is no home to fall back to, and losing your place is not a
detail — it is the entire difference between a hub you explore and a hub you
visit.

So `navStack` is an array of plain entries (`{view: "detail", id, kind}`) and
`view` is derived from its last one. The **live** state of the top screen — its
cursor, its filters, its season — stays in ordinary properties, because that is
what the views bind to; `push()` snapshots it into the entry being buried and
`pop()` reads it back. Reassigning the array is what notifies; the snapshot
mutates an object nothing binds to and is therefore free. Popping the last entry
is what closing means, so Escape from the hub still closes and always did.

Two bugs came out of building it, both worth keeping:

**push() must come before mutating.** `openBrowse()` set the new filters and
then pushed. The snapshot reads live properties, so the new filters were filed
under the OUTGOING entry — a pop would return to the filters you left with.
Capture first, mutate second, everywhere.

**The detail cursor is a key, not an index.** `sections` is built from the
title's own data, so a page opens with only `["actions"]` and gains `"genres"`
*ahead of it* when the genres land. An integer cursor therefore means a
different band a second after it was set. Seen live: PageDown-ing through a
page, then watching the cursor jump back to Play and the page snap to the top
when a slow title finally answered. The cursor is now the section's name and
the index is derived — and `resetCursor()` moved out of `onTitleChanged` (which
fires on arrival) into the hub's `loadTitle()` (which fires on navigation).

### The memo: one open's answers, kept

Walking back out of person → title → person → browse re-runs every `dekho api`
call on the way — five for a detail page alone once its cast and similar art are
counted. So `ApiRequest` gained an optional `memo`: identical argv within one
panel-open answers from it synchronously and spawns nothing. Escape is instant
and free.

**Opt-in per call site, because staleness is per verb.** `title`, `episodes`,
`person`, `discover`, `genres`, `languages` and every `prefetch` describe things
that do not change while a panel is open. `history` must NOT be memoised — it is
re-fetched precisely because a film just moved it, and a memo there would have
silently frozen Continue watching. Bounded at 24 entries and cleared with the
visit.

### The detail page scrolls, and the sheet is opaque on purpose

Cast, facts and "More like this" do not fit on one screen at this type scale and
should not try to. The page is a Flickable over a **pinned** backdrop: the
hero's text scrolls up and away while the art stays, and an opaque sheet slides
over it. The bottom scrim already ended on the page colour, so at rest the seam
is invisible.

The sheet being opaque is not decoration — it is what lets a face be a real
circle for one rectangle node. Rounding a picture costs a framebuffer per
instance (§5), and a cast shelf plus a filmography is a dozen at once, so
FaceTile uses PosterTile's stroke-over trick: a ring in the page colour whose
inner edge lands on the circle. That only works over a flat known colour, which
is why the shelves live on the sheet and not on the backdrop, and why the cover
colour is a property rather than a constant.

**The ring is not §5's `2r`.** Taken literally at radius w/2 that gives a 2w by
2w cover reaching half a face past the tile — and on a shelf the next delegate
is drawn after this one, so every cover ate a crescent out of its neighbour's
right edge. The user caught it in the first build. A circle only needs the ring
to reach past the SQUARE'S CORNER, at w/√2 ≈ 0.707w against the circle's 0.5w:
an overhang of 0.22w puts the outer edge at 0.72w, past the corner and small
enough to stay inside the tile. The person page's portrait had the same bug
about to paint over the name under it.

The tile is also 1.35x the face it holds. w185 wants to be drawn near 185 px and
no wider — past that the cache is being upscaled — but "Helena Bonham Carter"
does not fit in 185 px of this module's card type, and the first build elided
half a shelf to "Helena Bonh…". The extra third goes to the label, not the
picture.

**One cursor over bands.** `sections` is the visible bands in visual order, so
Up and Down mean "the band above/below" without a lookup table and Left and
Right walk the band you are in. The episode list is the one vertical band, so
there Up and Down walk rows first and step out at the ends — the tvOS rule, and
the only one that does not strand a twenty-row list. It also means the cast
shelf is thirteen keypresses below a season of Breaking Bad, measured on exactly
that page, so PageUp/PageDown jump a whole band.

**Wheel speed.** Flickable's built-in wheel step is tuned for a desktop scroll
area; on a 1963 px viewport of shelves it is more than a dozen notches to the
bottom, and the user's verdict was "scrolling feels too slow". A notch is now a
quarter of the viewport, riding the same animation the keyboard uses, and it
accumulates against the animation's TARGET rather than its current position — so
spinning the wheel does not lose the distance the in-flight animation has not
covered yet. The animation is explicit rather than a `Behavior on contentY`,
which would also fight every flick.

### Genres finally earn their chips

§9 rejected a genre chip row on the hub because genres are kind-specific in TMDB
("Action" for films, "Action & Adventure" for series) and one shared row would
have quietly emptied one of the two rails. On a detail page the kind is not
ambiguous — the chip belongs to one title — so the genres that were a
comma-joined tail on the meta line are now controls that open Browse filtered to
that genre AND that kind. Switching kind inside Browse clears the genre for the
same reason it was never shared: an id that means Action for films means
something else, or nothing, for series.

`--genre` takes a name or an id, and this module hands it both: the sidebar
knows ids because it fetched the list, a detail chip only ever had the name TMDB
printed. Normalising to the id as soon as the list arrives is what makes the
incoming genre show as *chosen* rather than as a stranger.

### Browse is an accordion, not a dialog

Six facets with up to twenty values each is four hundred pixels of chips laid
out at once, and a modal picker per facet is three clicks to change one thing.
The sidebar is facet rows that open one at a time: one flat index for the
keyboard, an obvious click target for the mouse, and every row shows what it is
currently set to without being opened. Genres and languages are fetched the
first time Browse is opened and not before — a hub open must not grow two more
processes for a screen most opens never reach.

`--cast` is wired to a real path rather than left plumbed and unused: the person
page's "Browse their titles" (and Ctrl+B, which means Browse everywhere in this
module) opens the same filmography with the whole facet sidebar over it. A
person scope is not a facet — it arrives from a person page and has no sidebar
row, so it leads the results caption and Escape is how you leave it.

### A trailer is a different unit, and the panel gets out of its way

`bin/dekho-play` grew `--trailer`: `dekho trailer --json` under
**`dekho-trailer.service`** instead of `dekho-play.service`. That name is the
whole point — §3's "one playback at a time" stop is what makes the Play button
safe, and sharing it would mean glancing at a trailer kills the film you are
forty minutes into. Measured, both active at once:

```
dekho-play.service     active     (the film)
dekho-trailer.service  active     (the trailer)
dekho-play --trailer --stop  →  play: active, trailer: inactive
```

The session-file sweep is **per prefix** for the same reason. The film's
per-run files are `session-*.ndjson` and the trailer's are `trailer-*.ndjson`,
because a sweep that unlinked the file the other mode's running unit is writing
to would leave the panel's `tail -F` waiting on a name that never comes back —
a trailer would have silently blanked the film's progress view. Within one
prefix the sweep is safe: starting a run in a mode has just stopped that mode's
previous unit. Two tails, two session objects, one `foldEvent` — what differs
between a film and a trailer is what an EXIT means (the film refreshes history;
a trailer is not watching the film and dekho does not record it as one).

**And the panel closes itself.** A film's wait is worth narrating — releases are
looked up and the swarm is measured before mpv launches, which is minutes, and
that trail is the whole reason the playback view exists. A trailer has no wait:
mpv is up in a second on a YouTube stream, and this surface is a fullscreen
OVERLAY layer, so the panel sat on top of the very thing it had just started.
User's verdict: *"mpv can't be visible because panel overlay on top."* It hides
on the `playing` event, not on the button press — a trailer that cannot be found
has to leave its error somewhere you can read it.

The real fix is to stop being an overlay at all: as an ordinary niri window the
floating mpv would sit above it for free, and the §6 keyboard-grab bug class
would go with it. Agreed with the user, deferred to its own change.

### Where you were survives a toggle — enforced by eviction, not by code

Closing used to mean finished (the emoji and clipboard pickers' rule, and the
right one at three screens). At five screens and a back stack it is the wrong
trade: you toggle the panel away to watch the trailer you just started, and come
back to the top of the hub having lost the page you were reading. `hide()` now
keeps the stack, the query and the memo.

The old rule is not lost, it is **delegated to the loader**. The surface is
`evictable` with a 45 s grace window (shell.qml), so a panel closed and
forgotten is destroyed — stack, memo and sixty decoded posters together — and
the next summon is a cold hub with an empty query. Nothing in the module has to
enforce "finished"; staying closed already does, and it does it for the pixmaps
too. A summon that lands back on a playback view drops its session and restarts
the tail, because `tail -n +1` replays the whole file and folding it onto the
events it already had would double the trail.

### What it cost

| | before (§10) | after (3 runs) |
|---|---|---|
| cold start | 211 ms | 250 / 183 / 218 ms |
| idle RSS | 308 MiB | 304 / 304 / 305 MiB |
| idle CPU (60 s) | 0.45% | 0.35 / 0.283 / 0.300% |

Unchanged, as it has to be: nothing new runs while the panel is closed, and
every screen added here fetches only when it is drawn. Cold start is quoted as
all three runs rather than the best one because a single number here is a lie —
the 250 ms run was on a box six minutes into its uptime with three other agent
sessions on it, and the spread is what noise looks like on this machine. RSS and
idle CPU are the numbers that would have moved if anything had leaked, and both
came back very slightly better.

Per-screen request counts, all on demand: a detail page is 1 + up to 4 prefetch
(poster w342, backdrop w780, faces **w185**, similar w342) + 2 for a season; a
person is 1 + 2; Browse is 1 + 1, plus genres and languages once per visit.
w185 is the third size this module fetches and lands in its own cache directory,
so it needs its own directory guard for exactly the reason §6 gives — a path
built against `""` resolves to the filesystem root.

### The one field worth wanting

Everything the contract promised arrived and rendered. `countries[]` comes back
as ISO codes (`["DE","US"]`) rather than names, so the About block says
"DE, US"; `languages[]` next to it is already names ("English, German,
Spanish"), which makes the pair read as an inconsistency rather than as a
shorthand. Not worth a change to dekho on its own — noted for whenever that file
is open anyway.

## 12. The hub becomes a window — 2026-08-20

§11 ended by promising this, and the reason was one sentence long: the panel was
a fullscreen surface on the **Overlay layer**, which is above every window on
the screen, so the mpv it had just launched came up *behind the thing that
launched it*. The trailer path worked around that by hiding itself on the
`playing` event. That is a patch on a surface, not a decision about trailers,
and it was the third symptom of the same cause — §6's keyboard bug was the
first, the scrim and the click-to-dismiss the shell never wanted were the
second.

The user's call, verbatim: *"instead of overlay layer, should we make it like
application? so panel will open in niri window so mpv floating will always be on
top of niri window."*

So `OverlaySurface` is gone from this module — and only from this module; the
five other surfaces that share it are untouched — and the hub is a
`Quickshell.FloatingWindow`, an ordinary xdg-toplevel that niri manages like
anything else.

### Not fullscreen, and that word is the whole change

**niri draws a fullscreen window ABOVE the floating layer.** Measured
2026-08-20 with a bare Quickshell window and a floating mpv on the same
workspace: as a maximized column mpv sat on top of it, and one
`fullscreen-window` later the window covered both the mpv *and the bar*. A
`fullscreen: true` anywhere in this change would have looked identical to the
old overlay and undone all of it, silently.

The rule in `home/dot_config/niri/config.kdl` therefore says `open-maximized`,
which is a full-width **column** — 3467x1914 of this desk's 3490x1963, the bar
and the gaps still visible — and floating windows stay above it.

### It is matched by app-id AND title, because app-id is not ours

Every Quickshell toplevel in the session is `org.quickshell`: Qt sets app_id per
**process**, from `QGuiApplication::desktopFileName()`, not per window. There is
no per-window knob to reach for and none was found. So the window rule matches
the pair — `app-id=r#"^org\.quickshell$"# title="^Movies & TV$"` — exactly as
the chromium sign-in rule above it does, and safely for the same reason
(`open-*` is evaluated once, at map). The title is `windowTitle` in Dekho.qml
and the two spellings are a matched pair; the module's `raiseWindow()` looks
itself up by the same pair.

Two rules elsewhere had to learn about it, because the hub is now something
window rules can see at all:

- config.kdl's `opacity 1.0` exemption gains `org.quickshell`. The base
  0.985/0.96 pair is a focus cue for **app** windows; the hub is opaque
  surface0 on purpose (§10 — a cinema is a room with the lights off), and at
  0.96 unfocused the wallpaper showed through the backdrop art.
- `Services/Blur.qml`'s fragment excludes it from both the blur rule and the
  0.95/0.9 pair. The shell is not an app window, and blurring a wallpaper
  behind a maximized opaque window is a pass with nothing to show for it.

### `toggle` had to grow a third answer

As a layer surface `toggle` meant two things, because an Overlay surface is
either up and above everything or not up at all. A toplevel has a state it
never could: mapped, but behind the mpv it started, or scrolled off, or on a
workspace you left. Hiding in *that* state is the wrong answer to
Mod+Ctrl+Alt+M — you pressed it to look at the thing.

```
not open                         → open it
open but not focused / elsewhere → focus it, bringing its workspace with it
open and focused                 → hide it
```

The middle case must never be an unmap+remap: that is a **new window** to niri,
re-running the open animation and re-picking a column every time you glance at
it. Verified by window id — a raise leaves the id alone (16 before and after,
across a workspace switch), where an open is a new one. Focus is read from
`Window.active` on the key catcher, which is one property and no subprocess;
only the raise branch spends anything, and it spends the same two-step the mail
panel's Emacs raise does (`niri msg --json windows | jq` for the id, then
`focus-window --id`). Qt's `requestActivate()` was the tempting zero-process
alternative and is not available: activating a Wayland toplevel needs an
xdg-activation token minted from a recent input event, and the input that
triggers this went to niri's keybind or the menu's layer surface, never to this
window.

`qs ipc call dekho {toggle,show,hide,search}`, the keybind and the Menu row all
still do what they did; `show` now raises an already-open window instead of
re-taking a focus that no longer needs taking.

### The trap: a compositor close destroys the binding

`visible: dekhoRoot.opened` is the obvious way to write this and it is wrong.
**niri's close-window (Mod+Q) unmaps a toplevel by WRITING `visible = false` on
it**, and an assignment destroys the binding underneath. Measured on the probe:
after one `close-window`, setting the property the binding came from did
nothing at all — the window was gone and unreachable.

Left that way `opened` would have been stranded at true for ever, which is not
a cosmetic bug: `SurfaceLoader` derives `surfaceOpen` from exactly that
property, so the grace timer would never arm and the whole tree — stack, memo,
sixty decoded posters — would have stayed resident until the next shell
restart. §4's "nothing exists while the panel is closed" would have been
quietly false for the one close the user is most likely to reach for.

So the direction is reversed: `panel.visible` is assigned by show()/hide() and
never bound, `opened` reads it back, and `didOpen()`/`didClose()` hang off the
window's own `visibleChanged`. A compositor close now stops both tails and arms
eviction exactly as Escape does, because it *is* the same code path.

### The focus workaround is gone, and it was checked the way it was found

§6's bug — the panel holding the whole keyboard and answering nothing after one
hide/show — is a property of `WlrKeyboardFocus.Exclusive` on a layer surface.
`show()`'s unconditional `Qt.callLater(forceActiveFocus)` and OverlaySurface's
`onVisibleChanged` re-take were both that bug's dressing.

Both are deleted. A toplevel is activated by the compositor and Qt hands the
focus to the scene's focus item when it is; `focus: true` on the key catcher is
the only focus statement left in the module. Verified the way the original was
found rather than by reading: on a bare FloatingWindow with no
`forceActiveFocus` anywhere, hide → reopen → type, and the keypress arrived.
Then again on the real hub, and again on the hardest version of it — activating
the **Menu row**, where a layer surface with an exclusive grab is dismissing at
the moment the toplevel maps. The very next keystroke went into the search line.

### The trailer just plays now

`appendTrailerLine()`'s `hide()` on `playing` is removed outright. mpv floats
above the window, so a trailer plays in front of the hub and the playback view
keeps narrating underneath it — which is also what makes Escape-ing back out of
it land somewhere. The error path that the `playing` guard existed to protect
is unaffected: a trailer that cannot be found still leaves its error on a view
that is still on screen.

The unit separation §11 measured is unchanged, re-measured here: a film
(`systemd-run --user --collect --unit=dekho-play -- sleep 240`) and a real
trailer active at once, and `dekho-play --trailer --stop` left
`dekho-play.service` **active**. A `qshell-relaunch` with the film unit running
left it active too — different slices, as §3 says.

### It survives being made small

The layout claim in §10 — every dimension a proportion of the surface — held
without one arithmetic change, because `panel.width`/`panel.height` are window
dimensions now instead of screen dimensions. Checked rather than assumed: at
half width (1726x1914) the hero still reads and two rails are still visible.

A floor was worth adding. `minimumSize: Qt.size(640, 400)`, and niri honours it
exactly — `set-window-width 300` gave 640, `set-window-height 200` gave 400. At
that floor the hub is cramped but coherent (search line, hero title, meta, one
rail of two posters); much below it the hero has no room for a title and the
rails stop being rails.

### What it cost

| | before (§11, 3 runs, same morning) | after (5 runs) |
|---|---|---|
| cold start | 250 / 183 / 218 ms | 196 / 256 / 220 / 268 / 238 ms |
| idle RSS | 304 / 304 / 305 MiB | 306 / 307 / 307 / 307 / 308 MiB |
| idle CPU (60 s) | 0.350 / 0.283 / 0.300% | 0.350 / 0.317 / 0.300 / 0.267 / 0.733% |

Five runs after rather than three, because three looked like a 2 MiB rise in
RSS and that was worth either finding or ruling out. Read together the numbers
say the machine, not the change: cold start drifted up over the same interval
(183–250 before, 196–268 after) and idle CPU threw a 0.733% run that is more
than double anything this shell has ever measured — the desk had three agent
sessions and this session's own testing on it, which is exactly the caveat §11
attached to its own 250 ms run.

The structural argument is the stronger one, though. Nothing here executes at
startup, and while the panel is closed the module is not merely idle but **not
instantiated at all**: `SurfaceLoader.wake()` is reachable only through
`summon()`, the bench never summons anything, and after eviction the tree is
gone again. So RSS was not left to stand as a proxy — the behaviour it stands
for was tested directly, on both sides of the 45 s window. Reopening inside it
landed back on the detail page it left (stack and memo kept, §11); reopening
after it gave a cold hub with an empty query.

### Two things that bit, neither of them the window

**A NUL byte in Dekho.qml.** The memo's cache key is `args.join(…)` with a NUL
separator — correct, and the right separator — but it had been written as a
literal 0x00 byte in the source. Every `grep` and `rg` over the file therefore
answered "binary file matches" and printed nothing, which is a landmine for
anyone who ever greps this module (it cost the first ten minutes of this
change). It is now the escape `"\u0000"`: the same byte at runtime, and
the file is text again.

**A detail backdrop can arrive blank, and it predates this change.** Seen live
walking the graph: the second title opened from a person page had no hero art,
with `Cannot open: …/w780/bs32Ds4L8VADGjBVasSK1ASU7OW.jpg` in the journal for a
file that exists on disk now. `detailBackdropDir` is set by the prefetch's
`onLoaded` and never cleared on navigation, so title B's path is built against
title A's still-valid directory *before* B's prefetch has run — §6's bug class
again, with a stale directory in place of an empty one, and the directory guard
cannot see it. Left alone deliberately: it is a request-sequencing bug in code
this change does not touch, and it wants its own look.

## 13. Driving it as a window — 2026-08-20, same afternoon

Four things the user hit within an hour of the window landing. None of them is
about the window; all of them are about the hub finally being used like an app.

### A row of six should be a row of six

Every grid sized its cell from `posterWidth + gutter` and let `GridView` fit as
many as it could, which leaves the remainder as dead space against the right
edge — on the desk, most of a seventh card, so a "row of six" ended in the
sliver of a cut card. The user's verdict: *"rows should fill whole column
automatically. If 6 column showing per row and 6 is there then they should fill
whole row."*

The fix is to invert which number is derived. `posterWidth` becomes a **target**
that decides only the column COUNT, and the cell is then the row divided by that
count:

```
columns   = floor(width / (posterWidth + gutter))
cellWidth = floor(width / columns)
tileWidth = cellWidth - gutter
```

All three grids — Browse results, the hub's search results, a person's
filmography — and their cursors, which now read `grid.columns` rather than
re-deriving it, because a cursor that thinks a row is seven wide when it is six
skips a card on every Down. The containers also lose one gutter off the right
margin so the last poster ends on the edge pad rather than a gutter inside it.

The rails are deliberately NOT part of this: a shelf's last card bleeding off
the right edge is §10's way of saying "this shelf continues", and a shelf that
ends flush would be claiming it does not.

### The hub is one page now

*"homepage scrolling is too slow. Make it like single page"*, then *"in hero,
scrolling not working. Scrolling should work there also — shrink then fixed"*,
then *"can we shrink hero banner with nice animation so it feels awesome"*.

Three complaints, one cause: the hero was a fixed 52% band that never moved, and
the shelves scrolled in the ~48% left over at Flickable's default ~60 px step. So
the biggest thing on screen was inert, the part being read had half a screen to
do it in, and the wheel crawled.

- **The hero collapses to 24% as you scroll, then holds.** Driven straight off
  `contentY` rather than by an animation of its own, so it tracks a wheel step, a
  flick and a keyboard rail change identically — the motion IS the scroll's,
  which is the only way the two stay in sync. The synopsis and key hints fade
  and give up their height on the way down, which is what leaves the title and
  meta line legible in the shrunken band.
- **A notch is a page** (the user's words), where the detail page settled on a
  quarter in §11.
- **The wheel works over the hero.** A Flickable only sees wheel events that land
  inside it, and the hero is not inside one, so more than half the screen was
  dead to the wheel. The step is now a function on the module shared by handlers
  on the hero, the shelves and the search grid.

### The collapsed header, second attempt

The first build of the collapse was judged on sight and failed: *"sticky header
not looks good."* Three separate faults, and only the third was cosmetic.

**The art was re-cropped, not uncovered.** Both hero plates were
`anchors.fill: parent` on a band whose height was now animating, so
`PreserveAspectCrop` re-derived the crop on every frame — a 16:9 still squeezed
into a 24% band is an arbitrary horizontal slice (the back of someone's head and
some skyline), and it *slid* as you scrolled because the crop moved with the
height. The fix is to stop the art having a height that changes at all: the
plates are page-sized and pinned (`heroPlateHeight`/`heroPlateY`), and the band
is a clipping window onto them. Collapsing now uncovers less of a picture that
has not moved. `heroPlateY` offsets the plate so the RESTING band still shows
its vertical centre, which is where a backdrop's subject lives and what the hero
framed before any of this.

This is the user's *"arts will be full page fix background"*, as far as it can
go. It cannot go further: **PosterTile's rounded corners are a stroke in
`surface0`**, so anything drawn over live artwork gets a visible page-coloured
ring on all four corners — sixty of them on the hub, and FaceTile has the same
deal (§11). Artwork behind the shelves would cost either that or a framebuffer
per card. So "full page background" means a full-page plate that the opaque page
progressively covers, not artwork under the posters.

**The bottom was a hard cut.** The dissolve into the page was a fraction of the
band (`0.82 → 1.0`), so it thinned as the band did until the art ended in a line
straight across the first shelf's posters. It is a fixed depth now
(`heroFade`), so the art always dissolves over the same distance and the band's
bottom edge is never an edge.

**The title did not step down.** 73 px of hero type in a quarter-height band
crowded the meta line into the boundary. `heroTitleSize` interpolates hero →
railTitle with the collapse, landing on the size the shelf captions already use,
and the title drops to one line past the halfway point.

Two more things had to be got right, and the first one bit:

**A ListView with a header starts at a NEGATIVE contentY.** `originY` is
`-headerHeight`, and contentY only reaches 0 once the header has scrolled away.
Dividing `contentY` itself therefore meant the shelves climbed the hero's whole
height *before* the hero began to shrink — and rode up over its title on the
way, which is exactly what it looked like. Measured: `contentY -536` at rest
against a 536 px header. The collapse is `(contentY - originY) / heroRange`.

**The rail list's geometry must not depend on the collapse.** It is anchored at
`heroMin` and carries a spacer header of `heroRange`, rather than being anchored
at the live hero height. Anchoring it to the collapsing hero would resize the
Flickable, which moves contentY's own maximum, which feeds straight back into
the collapse — a loop that oscillates at the bottom of a short list. For the
same reason `heroFull`, not the live height, is the budget poster sizes are
measured against: a tile size that changed mid-scroll would re-lay-out and
re-decode sixty cards, which is the one thing this module has spent its whole
life avoiding (§5).

### Tab is "the next thing"

*"Can we also enable tab/s-tab navigation?"* — and the useful answer is not
"another arrow key". The arrows are 2D and screen-shaped: along a rail, across a
row, between bands whose very existence depends on what data has landed (§11).
Tab flattens whichever screen you are on into ONE order and walks it, so a page
can be walked without knowing its shape:

| screen | Tab |
|---|---|
| hub shelves | along the rail, off its end into the next one |
| search / Browse results / filmography | the next card, crossing rows |
| detail | the next thing in the band, then into the next band |
| Browse sidebar | the next facet row |

Shift+Tab is its exact inverse, which is why stepping backwards across a
boundary lands on the FAR end of the band it arrives at rather than the near
one. `Model.tabDelta()` is shared because Shift+Tab is not one key: Qt normally
sends `Key_Backtab`, but a `Key_Tab` carrying ShiftModifier reaches the handler
on some paths, and a Tab that silently went forwards when shifted would be worse
than no Tab at all.

Tab does NOT change pane in Browse. Left and Right already cross between the
sidebar and the results — the sidebar is literally to the left — and a "next"
key that sometimes meant "elsewhere" would be hardest to undo on the one screen
with two hundred results in it.

### Playback needed an ending

*"after click Stop Playback, nothing changed on that screen, just Stop Playback
button gone."* Correct, and worse than it sounds: `stopPlayback()` stops the
unit and drops the tail, so the last line the view ever saw is the green
"Playing …" one. The screen kept the green headline, the "mpv has it, this panel
can close" line and a frozen swarm meter, and lost only the button. There is no
event to wait for either — the unit is SIGTERMed, so the `exit` line that ends a
normal run may never be written, and the tail is gone regardless.

Building the flag for it exposed the bigger half: a trailer that simply
**finishes** leaves `running` false with nothing else changed, which is the same
stale screen for the same reason. So the terminal state hangs off `running`, not
off the Stop button, and the button only picks the word:

| | headline | says |
|---|---|---|
| Stop pressed while playing | Stopped | mpv closed, position remembered |
| Stop pressed before mpv | Cancelled | nothing was watched |
| ran to the end | Finished | as above, per kind |
| errored | *(its own line, kept)* | the error, in the error colour |

The live-only furniture (meter, peer count, the "mpv has it" line) goes with it,
the trail stays because why you stopped is worth reading, and the pill becomes
**Back to the title** rather than leaving a gap where a control had been — a
missing button is what made a stop read as a click that did nothing. A trailer's
line says a trailer is not recorded as watching the title, because it is not,
and claiming otherwise would be inventing a feature.

### What driving it on a live session cost

Two traps worth writing down, neither in the code:

**`ydotool mousemove -a` opens niri's overview.** Absolute pointer events from a
freshly created virtual device read as a gesture, and separately, slamming the
pointer to the top-left corner as a positioning anchor hits niri's **hot corner**,
which opens the overview too. Both interrupted this session repeatedly. Relative
moves away from the corners are the way to place a pointer here — but they go
through pointer acceleration, so they cannot be aimed precisely enough to click a
specific button, which is why the Stop path was verified through the ending it
shares with a natural finish rather than by clicking.

**A literal NUL byte makes a file un-greppable** — §12 covers it; it is repeated
here only because it cost the first ten minutes of the day and the symptom
(`grep` printing nothing, silently) looks like a bad pattern rather than a bad
file.

### Two request-ordering bugs, both "state from the previous screen"

Found by driving the change, fixed after it. They are the same shape: something
built a path or skipped a fetch using state that belonged to the screen before.

**The detail backdrop was blank on any title the hub had not already focused.**
§6's bug, back in a different hat. Every w780 backdrop lands in the SAME cache
directory, and `detailBackdropDir` was never cleared on navigation — so opening
a second title built its path against the first title's still-valid directory
before its own prefetch had run. Worse than a flicker: when the prefetch finally
answers it assigns *the same directory string*, so nothing in the binding
changes, and Qt's Image has already cached the miss and will not retry
(PosterTile's header warns about exactly this). The hero stayed blank until you
navigated away and came back.

A per-directory guard cannot express "is THIS file there yet", so the guard is
per-FILE — and the hub's hero already keeps exactly that map, `heroDone`. The
detail backdrop prefetch now records its files into the same map and the page
reads `detailBackdropReadyDir`, which is `""` until this title's own still is on
disk. One map of "w780 files known to be on disk", two consumers, and the bug is
gone by construction rather than by another flag someone has to remember to
reset. Verified on the exact repro — a person page opened from a detail page,
then a credit the rails had never shown (Se7en): art present, no `Cannot open`.

**Stopping a film left Continue watching stale.** The rail is refreshed when a
run ends, from the `exit` line in the NDJSON — but a Stop SIGTERMs the unit and
drops the tail in the same breath, so that line never arrives. The rail kept the
position from before the stop until the panel was next opened.

The fix needed an ordering guarantee, not just an extra fetch: dekho writes the
history on its way out, and `systemctl stop` **returns before the cgroup is
empty** — bin/dekho-play's own start path already says so and already had a
bounded wait for it. That wait is now a function used by both paths, so `--stop`
returns only once the unit is really gone, and the panel runs the stop as a
tracked `Process` and re-fetches history on its exit. Measured: `--stop` against
a unit whose TERM handler sleeps a second takes 1019 ms and leaves it inactive.

Being in the shell's cgroup is fine for this one, unlike playback (§3):
`systemctl --user stop` has already been handed to the user manager before
anything could kill the helper, so a shell that dies mid-stop still stops the
film — it only loses the re-fetch, which the next open does anyway.

### What it cost

210 ms cold start / 307 MiB idle RSS / **0.100%** idle CPU, against §12's five
runs. Unchanged, as it has to be: everything here is layout and key handling
inside a surface that is not instantiated while the panel is closed. The idle
CPU coming back at 0.100% — the lowest this shell has measured — is also the
answer to §12's 0.733% outlier: that was the desk being busy, not a leak.

The one thing worth watching is that the grids now decode slightly WIDER
posters, because a tile grows to absorb the row's remainder instead of leaving
it as dead space. `sourceSize.width` is still bound to the tile's own width, so
they decode at the size they are drawn at and no larger — the §4 rule holds, the
number it holds at is just a few per cent bigger.

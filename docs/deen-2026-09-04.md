# An Islamic hub in the shell — plan, 2026-09-04

User ask, in their words: *"We have prayer time and random verse. Since I am
muslim so I want to make my device a perfect islamic hub"*, then *"Can we make
a Islamic Hub like Movie/TV Series hub? in islamic Hub, we will add all islamic
features which need?"*, then *"If need we can build a rust cli like dekho. so
plan properly also check how AI can help here. I want to be proper muslim."*

The situation that decides every priority below, also in their words: they have
forgotten how to read the Quran, forgotten many surahs, forgotten how to pray
properly, cannot recall some surahs and duas during salat, and are worried the
pronunciation of what they *do* remember is wrong.

So this is not a reference app. Every screen has to answer one of those five,
and the ones that only decorate the desktop can wait.

## 2. The shape: dekho's architecture, unchanged

`shell/Modules/Dekho` already solved this problem. The Islamic hub is the same
building with different rooms, and the mapping is one-to-one:

| Dekho | Here |
|---|---|
| Fullscreen `FloatingWindow`, opaque, `blurable: false` | same |
| `SurfaceLoader` marked `evictable` — nothing exists until summoned | same, and it matters more: Arabic fonts, decoded art and audio buffers |
| `Style.qml` as the translation layer over `theme` | same |
| `screens/` + `components/`, real Qt focus, Tab walks a screen | same |
| `dekho api …` → one JSON object on stdout, diagnostics on stderr | `deen api …`, identical contract |
| The shell speaks no HTTP and holds no key | same |
| Children under `setpriv --pdeathsig TERM` | same |
| IPC target + keybind + vicinae row + niri window rule on title | same |

**The one deliberate divergence.** Dekho §9 has no `Services/` and no bar widget
because nothing about films needs to exist while the panel is closed. Prayer is
the opposite — it must tick while the hub is shut, and `PrayerService.qml`
already does. So: **the bar keeps Prayer and only Prayer; every other screen
lives in the hub and costs nothing when closed.**

Working name `deen` (দ্বীন), parallel to `dekho` (দেখো). Changeable.

## 3. The Rust CLI

Same rationale as dekho §2: the shell parses stdout blind, TLS and JSON never
run on the shell's event loop, there is exactly one implementation of each
question, and everything works from a terminal too.

```
deen api ayah <s>:<a>            one ayah: uthmani, words, translations, audio keys
deen api surah <n>               a surah's ayat
deen api search <query>
deen recite --ayah <s>:<a> [--wav F | --record]
                                 {ops:[{op,ref,hyp,start_ms,end_ms}], wer}
deen audio prefetch <keys…>      ayah/word audio into ~/.cache/deen/, answers the dir
deen hifz due | grade <ayah> <0-5>
deen times --lat --lon --method --school
deen dua list | show <id>
deen salat steps --madhhab hanafi
```

**Unlike dekho, the data is local.** TMDB changes hourly; the Quran does not.
The Uthmani text, a Bangla translation, an English translation and the
word-by-word index ship as files (single-digit MB) instead of an API call per
open. Consequences: the hub works with no network, there is no key to protect,
and there is no rate limit to respect. Only *audio* is fetched on demand and
cached.

State in `~/.local/state/deen/` (hifz history), cache in `~/.cache/deen/`
(audio). Recitation WAVs are scratch — deleted after scoring, never uploaded.

## 4. How AI helps — and the rule it does not get to break

The user asked me to check this specifically. There are three honest answers.

### 4a. ASR for recitation checking — the real win, and it is free

Verified on this machine rather than assumed:

- **voxtype is a compiled binary, not Python.** There is no torch, no
  faster-whisper, no numpy here, and no need for any.
- Its whisper engine is **whisper.cpp/ggml** — `ggml-small.en.bin` sits in its
  models dir, and `whisper.model` documents "an absolute path to a .bin file".
- `voxtype transcribe` is a **one-shot subcommand, separate from the dictation
  daemon**, so none of this touches Alt-Alt.
- Global `--model`, `--language`, `--threads` all apply to it. Flag plumbing
  verified end to end: `voxtype --model <path> transcribe f.wav` loaded the
  model, ran VAD, exited 0.
- **ggml builds of the Tarteel Quran model exist** —
  `ram-a-dhan/tarteel-whisper-quran-ggml`, fp16 141 MB and q8_0 77 MB.
  Upstream `tarteel-ai/whisper-base-ar-quran` reports 5.75% WER on Quranic
  Arabic.

So the entire recitation checker is one model file and no new runtime:

```
pw-record → 16k mono wav
voxtype -c quran.toml transcribe recite.wav
normalise both sides → Levenshtein align against the known ayah → per-word status
```

**Three traps, all hit and all fixed. `deen`'s installer must handle each.**

1. **`--model <abs path>` is silently ignored.** The flag exists and is
   documented as accepting a path, but `transcribe` loads the *configured*
   model anyway — the run says `Loading whisper model from
   ".../ggml-base.en.bin"` while claiming to honour the flag. Every result
   before this was found came from the English dictation model. The path must
   go in `[whisper] model` in a config file passed with `-c`.

2. **`whisper.initial_prompt` bleeds in from the dictation config.** The user's
   prompt is *"Technical discussion about Laravel, PHP, React, TypeScript,
   pnpm, PostgreSQL…"*, which biases so hard toward English that Arabic audio
   comes out as Latin transliteration: `Bismillahir Rahmanir Rahim`. Clearing
   it is not enough — the script only anchors once the prompt is itself
   Arabic. A short neutral non-Quranic sentence works; do **not** use an ayah,
   which leaks the answer into the decode. Hence a dedicated `quran.toml`
   rather than mutating the dictation config.

3. **Every published ggml conversion of this model is broken the same way.**
   The header declares `n_text_ctx = 1024` while
   `decoder.positional_embedding` is the standard `448`, so whisper.cpp
   refuses it: *"tensor 'decoder.positional_embedding' has wrong size … shape:
   [512, 448, 1], expected: [512, 1024, 1]"*. Checked `ram-a-dhan` (both
   quantisations) and `payrawsa` — all carry `1024`, so it is the converter,
   not a bad upload. The tensor is correct; only the header lies. Fix is a
   four-byte write at **offset 24** (`4` magic + 5 int32s), `1024 → 448`.
   After the patch the model is flawless.

### Benchmark, Al-Fatiha, Husary

Both quantisations, after the header patch:

| | fp16 (142 MB) | q8_0 (78 MB) |
|---|---|---|
| Ayat exact | 6 / 7 | 6 / 7 |
| Overall WER | 1 word in 29 — **3.4%** | identical |
| 7 ayat | 10.1 s | **8.1 s** |

Output arrives fully vowelled — `الْحَمْدُ لِلَّهِ رَبِّ الْعَالَمِينَ` — which
the normaliser strips. The single miss is 1:6, `ٱهْدِنَا` heard as `فِيهْدِنَا`.

**q8_0 wins and is installed** at `~/.local/share/voxtype/models/
ggml-quran-base-q8.bin`: byte-identical transcriptions to fp16 here, 45%
smaller, 20% faster.

Two caveats on that number. Husary is in the everyayah corpus this model was
fine-tuned on, so 3.4% is optimistic. And identical output on seven ayat of
clean professional recitation does not prove the quantisations agree on a
learner's voice — revisit if q8 disappoints in real use, since it is only a
path in a config file.

**The normalisation is the actual engineering, and it is where this feature
lives or dies.** Prototyped and verified before committing to Rust
(`/tmp/quran-bench/align.py`). Strip harakat, the Quranic annotation signs
(U+06D6–U+06ED) and tatweel; fold every alef variant, alef maqsura, ta marbuta
and the two hamza carriers.

Then the trap. The dagger alef (U+0670) is **ambiguous against modern
orthography and no rule resolves it**: `ٱلرَّحْمَٰن` is written `الرحمن`
without an alef, but `ٱلْعَٰلَمِين` and `ٱلصِّرَٰط` are written `العالمين` and
`الصراط` *with* one. Deleting it is right for the first and wrong for the other
two; converting it to an alef is wrong for the first. Either choice makes
**three of Al-Fatiha's seven ayat report a mistake the reciter did not make** —
which, for someone already anxious that their recitation is wrong, is the one
failure mode that matters. So neither side gets an opinion: word equality
ignores alefs entirely. Verified both directions — orthographic variants score
0%, and `المستقيم → المستعين` is still caught at 33%.

### 4b. Timing, not transcription — the honest ceiling on tajweed

whisper.cpp emits token timestamps, and **the quantitative tajweed rules are
durations**: madd lengths are counted in harakat, ghunnah is held about two.
Those are measurable from timing without understanding the audio at all. That
is a real, buildable, later-phase feature.

**Correction, 2026-09-05: it is not gated on usage, it is gated on tooling, and
the tooling does not have it.** `voxtype transcribe` prints text and nothing
else — no `--json`, no timestamp flag, and `voxtype --help` offers none — and
there is no standalone whisper.cpp CLI on this machine, because voxtype links it
statically. whisper.cpp emits the timestamps; nothing surfaces them to us. So
this is not "phase 6 if phase 2 proves solid" (§6), it is a decision about where
transcription comes from, and it has to be made before any of the timing work
starts. Three routes, in order of what they cost:

1. **voxtype gains timestamp output.** Upstream (`hyprsyn/voxtype`), or a patch
   we carry. Cleanest by far: `deen` goes on shelling out and gains no runtime.
   Not ours to schedule.
2. **`deen` shells out to a whisper.cpp CLI instead** (`whisper-cli -oj`). Needs
   whisper.cpp installed — ask first — and leaves two transcription paths on the
   machine doing nearly the same job.
3. **Derive the timing from the WAV** by energy segmentation, no new dependency,
   but the word-to-audio alignment becomes ours to get right. A rule that tells
   someone their madd was short had better not be guessing.

The parts that are NOT blocked, so they do not get re-derived: the expected
length is already in the data — the tajweed spans name the rule (`madd_2`,
`madd_246`, `madd_6`, `madd_munfasil`, `madd_muttasil`), so how many harakat a
madd wants is read, never inferred. And the measure has to be **relative**: a
harakah has no fixed duration, it is one short vowel at the reciter's own tempo,
so the baseline comes from their ordinary syllables in the same ayah and the
madd is expressed as a ratio against it. That is what makes it work at any
speed, and it is also why it needs no calibration step.

One ceiling to state before building it. Timestamps are per *token*, and a madd
lives inside a word, so what is actually measured is "did you rush the word
carrying the six-count madd, relative to your own tempo here". That catches the
gross error — a 6 said as a 2, which is the one worth catching — and it cannot
say which vowel was shortened, nor tell 4 counts from 5. Which is exactly the
claim this section already licenses: *held long enough*, not *correct*.

**Articulation is not, and no amount of AI changes it.** Makhraj errors —
ص/س, ض/د, ق/ك, ط/ت — are exactly what a speech model's language prior silently
repairs: it hears an approximate sound, recognises the word from context, and
transcribes the correct word. The tool will say "right word" precisely when you
most needed to be told otherwise. Every open-source project claiming "AI tajweed
feedback" is doing word-level matching and calling it tajweed; the published
research covers four rules under lab conditions.

The technique that would work is goodness-of-pronunciation scoring — forced
alignment against a tajweed-aware phonemizer, scoring per-phoneme acoustic
likelihood. That needs raw model access, not a CLI. Phase 3, maybe never.

**So this screen's honest claim is: "you said the right words, in the right
order, and held the madd long enough." Not "your tajweed is correct."** It must
say so in the UI. Overclaiming here would give false confidence about the exact
thing the user is worried about.

### 4c. Claude for explaining and scheduling — never for asserting

The repo already has the pattern (`bin/crash-diagnose` shells out to `claude`).
Legitimate uses: explain an ayah in Bangla at the user's level, build a
memorisation schedule from hifz history, explain *why* a word was missed ("you
said المستعين — that is from ayah 5, you jumped verses"), draft encouragement.

**The hard rule, and it is the "I want to be proper muslim" part of the ask:**

> Generated text never stands alone as religious content. Every ayah, hadith,
> dua, translation and salat instruction comes from a fixed, versioned, on-disk
> dataset with its source shown. The model may explain, encourage, schedule and
> navigate. It may never assert.

An LLM's failure mode on religious content is confidently inventing a hadith
that does not exist, an ayah number that is wrong, or a ruling with no basis.
For someone rebuilding their practice from nothing, a plausible fabrication is
worse than no tool at all — they have no way to catch it. This is the same
class of rule as dekho's "the shell holds no key", and it gets enforced the same
way: structurally, by where the bytes come from, not by prompting carefully.

The Salat screen's content in particular is authored from a Hanafi source the
user supplies and **verified by a person before it ships**. I build the screen;
I am not the authority on what it says.

And the ceiling worth saying once: this rebuilds fluency, memory and confidence.
Articulation and fiqh want a teacher. The tool is for the six days between
lessons, not instead of them.

## 7. What phase 2 shipped

**`deen`** — a Rust CLI at `~/Sites/github/deen`, four dependencies (serde,
serde_json, clap, anyhow) and no HTTP client at all, because the text is local
and transcription shells out. `deen api {surahs,surah,ayah}` and `deen recite
<ayah> [--wav]`, one JSON object per call on stdout. 12 unit tests, including
the alef regressions in both directions and the silence-parsing case.

Stopping a recording is **stdin EOF, not a signal** — the panel closes the pipe
(`stdinEnabled = false`), which means no PID bookkeeping and no way to lose a
child with the microphone open. `--max-seconds` is the backstop.

The microphone is unmuted for exactly one recitation and restored after, on the
error paths too. bin/voxtype-mic-gate exists because voxtype recorded digital
silence for weeks; `deen` cannot use that gate because it never touches the
daemon, so it carries its own.

**`shell/Modules/Deen`** — `Deen.qml` (root, owns every request and the window),
`Style.qml`, `DeenApi.qml`, `screens/ReciteScreen.qml`. Evictable surface, a
real toplevel, `open-maximized` by a niri rule matched on title, reached from
the launcher as "Islamic Hub". No keybind and no `Services/Deen.qml`, both for
the reasons dekho gives. Space is the recitation pedal.

**`run_after_49-deen.sh`** — binary, text and model, each guarded independently.
The model download re-patches the broken header, guarded on the current value so
a future good upload is left alone.

### Two UI bugs the live panel found, neither visible in the code

**The ayah was painted red under the words "nothing was heard."** VAD returns an
empty transcription for silence, the aligner correctly calls every word missed,
and the screen rendered that verdict — telling someone whose microphone was
muted that they got every word of the Fatiha wrong. A recitation that did not
happen now has no verdict: the text stays plain and only the message speaks.

**The first layout was a form, not a page.** Anchored to the whole window, the
ayah sat pinned to the right edge and the translations to the left with two
thirds of the desk empty between them — the same verdict dekho's doc §10
records against its own first version. One centred column with a ~900 px
measure and the ayah on the only raised surface.

## 9. What phase 3 shipped

The **Read** screen: a surah, word by word, tajweed coloured, every word one
tap from hearing it — and the ayah number is the play button for the whole
ayah. `deen` gained `api surah` (words included, because 286 processes to paint
Al-Baqarah is not a screen), `audio` for word and ayah recitation cached under
`~/.cache/deen/audio`, and the tajweed spans.

**Eighteen rules are drawn as four families** — hold it longer, through the
nose, bounce it, not pronounced — with a legend on the page. Finer distinctions
(how many counts of madd, which idghaam) are real and deliberately not drawn:
they are a teacher's job, and guessing at them in colour would be the same
overclaiming §4b refuses.

### The Arabic source had to change, and three things forced it

All of `cpfair/quran-tajweed`, the word-by-word audio CDN and the reader index
into the same text, and being wrong is silent in all three.

1. **Tajweed offsets are defined against ONE pinned Tanzil file.** Against it,
   15,985 annotations land; against alquran.cloud's quran-uthmani, 53% do, and
   the drift is variable *within* an ayah (2:13 shifts by 0, 0, −2), so no
   constant offset recovers it.
2. **alquran.cloud splits waqf marks (ۛ) as whitespace tokens** — 82,456
   "words" against Tanzil's 77,878. The audio CDN is indexed by word position,
   so its numbering runs ahead on the 2,719 ayat that carry them. 2:2 is seven
   words on the CDN and nine there.
3. **Tanzil glues the Basmala onto ayah 1 of every surah** but Al-Fatiha (where
   it *is* ayah 1) and At-Tawbah (which has none). Left in: a Basmala inside
   Al-Ikhlas 1, word audio four words ahead for 112 surahs, and four words
   reported missing from every correctly recited opening ayah.

The Basmala is cut **by word count, not by matching the text** — surahs 95 and
97 spell it بِّسْمِ with a shadda the other 110 lack, so a literal comparison
leaves it in exactly two surahs. The tajweed offsets on those ayat shift by
what was cut. Verified against the CDN on sixteen ayat, first and middle: last
word 200, one past it 404.

### One QML trap worth keeping

A `height: visible ? implicitHeight : 0` on a Label is a binding loop — a
Label's implicitHeight is derived from its geometry, so it cannot also define
it. The Basmala heading is anchored past instead, and the list anchors to
whichever of the two is above it.

## 10. What phase 4 shipped

The **Memorise** screen: SM-2 over ayat, with the text hidden until you have
recited it. A review where you can see the answer measures nothing, and the
reason to build this on Recite rather than beside it is that **the grade comes
from the recitation** instead of from asking whether you knew it — the question
people answer generously.

`deen hifz add` takes an ayah or a whole surah, `due` returns the queue oldest
first with the text attached, `grade` records again|hard|good|easy, and
`recite` now suggests one from the accuracy it measured. All four buttons stay
live: the checker is wrong sometimes and the reciter is not.

Three scheduling decisions worth keeping:

- **Due dates are absolute timestamps, not calendar days.** A day boundary
  needs a timezone and buys nothing — an ayah reviewed at nine in the evening
  comes back at nine in the evening some days later.
- **An `Again` on a never-learned card is not a lapse** — you cannot forget
  what you never had — and it returns in ten minutes, not tomorrow, because it
  is still today's problem.
- **Ease survives a lapse.** An ayah is not harder because you had a bad
  morning, and resetting ease as well as the interval double-punishes it.

The accuracy→grade mapping is deliberately generous at the top (≥0.97 is Easy),
because the checker's own error rate must not cost the reciter a grade.

### Two bugs found by running it

**`DeenApi` prepended `api` to every call**, so `hifz due` went out as `deen api
hifz due` and came back a clap parse error. `hifz` and `audio` are top-level
verbs; the wrapper is `DeenCall` now and takes the whole argv after `deen`.

**The error it surfaced was clap's last line** — "For more information, try
'--help'." — which says nothing. It prefers a line starting with `error:` now.

### One extraction

`Reciter.qml` — both Recite and Memorise need the same record/stop/score
object, and two copies would have drifted. It lives at the module root and is
passed down, because a screen in `screens/` cannot see a type in the directory
above it (the same rule that put every request in the root).

## 11. What phase 5 shipped

Three additions to `PrayerService`, no new screen:

**The nudge**, on by default at 10 minutes. A toast at the moment a prayer
starts tells you that you are already late to begin; ten minutes of warning is
the difference between meaning to and going. `"nudge": 0` turns it off.

**Adhan sound**, off by default. `"sound": true` rings the freedesktop bell
already on every machine here; `"sound": "/path/to/adhan.mp3"` plays that
through mpv. Nothing is downloaded — which muezzin you hear five times a day is
not a choice a dotfiles repo should make for you.

**Salat mode**, off by default: silence the desktop for ~15 minutes after a
prayer, then put it back. A toast is additive and is what a prayer widget is
for; muting notifications is a side effect on unrelated software, and a call
missed because the shell quietly decided to is a worse failure than a toast you
did not want. `"salatMode": true` opts in.

Two things make it safe. **The restore only fires if DND is still where we left
it** — toggling it by hand during the window is a decision, and a timer that
stomps it fifteen minutes later would be the widget arguing with the user. And
**it declines to engage if DND is already on**, so it can never turn off a
silence the user chose.

Prayer notifications survive all of this for free: `Notifs.routeNotification`'s
bypass passes our own `qshell` sender by name, so a prayer call is not silenced
by a DND the user set, nor by the one salat mode sets.

### Verified by injection, since a real prayer is hours away

Today's cached Isha was rewritten to two minutes out with `nudge: 1` and
`salatModeMinutes: 1`. The nudge toast appeared on its minute ("🕌 Isha in 1
min / 22:03" at 22:02:03), `dnd` went `true` at the prayer minute — which is
proof the arrival path ran, since `beginSalatMode()` is only reachable from
`checkArrival()` — and `dnd` was back to `false` a minute later. The cache was
then deleted and real times refetched.

One thing that cost time and is worth writing down: **the notification history
in `notifications.json` is not flushed live, but `dnd` is written through
immediately.** Checking `past` for a toast that just fired shows nothing and
proves nothing.

## 8. Verified facts, so they are not re-derived

- Aladhan `school=1` is Hanafi Asr; default 0 is 61 min earlier in Dhaka today.
- voxtype is ELF, not Python; its whisper is ggml; `transcribe` is one-shot and
  independent of the daemon.
- **`--model <abs path>` is silently ignored by `transcribe`** — the model path
  must live in `[whisper] model` in a `-c` config. `--language` *is* honoured,
  but is not sufficient on its own (§4a trap 2).
- **`voxtype transcribe` emits text and nothing else** — no timestamps, no JSON,
  no flag for either (checked 2026-09-05), and voxtype links whisper.cpp
  statically so there is no CLI beside it to ask instead. This is what blocks
  madd timing (§4b).
- ggml Quran models exist at `ram-a-dhan/tarteel-whisper-quran-ggml`
  (fp16 141 MB, q8_0 77 MB; also tiny at 74/41 MB) — **all published
  conversions need the offset-24 header patch** (§4a trap 3).
- Post-patch on Al-Fatiha/Husary: 3.4% WER, q8_0 identical to fp16 and faster.
- Alef ambiguity (§4a) breaks 3 of 7 Al-Fatiha ayat unless matching is
  alef-insensitive.
- The omarchy ecosystem has **one** Islamic plugin,
  `husamemadH/omarchy-quattro-prayer-times`. Ours is ahead on caching and Hijri;
  its Hanafi Asr toggle, alert sound and bar countdown are worth taking.
- Linux's native Islamic stack (ITL, Minbar, Zekr, KPrayerTime) is a decade
  dormant. `0xzer0x/quran-companion` is the only live native mushaf. No tajweed
  feedback tool exists on Linux at all.

## 12. The redesign

User's words: *"redesign hub as like Dekho so it's looks premium and fully match
our theme"*, and mid-build: *"bangla and english fonts looks smaller"*, *"No way
to browse surah.. I have to go next/prev"*, *"Can we make better design for
this"*.

The diagnosis was one sentence: **every control was a bare `QtQuick.Controls`
default**, drawing itself in Fusion's palette rather than in the theme. That is
the whole reason the hub read as a settings form. Dekho has twelve ported
components; this had none.

`Modules/Deen/components/` now has thirteen. Six are Dekho's, copied rather than
imported — `GlassButton`, `Toast`, `EmptyState`, `StatTile`, `MeterRow`,
`AmbientBackground`, plus `ModalSheet` and `FocusNav.js`. **Copied, because a
cross-module `import "../Dekho/components"` would break the Islamic hub when the
movie hub retunes a chip**, and because they diverge here (GlassButton grew
`tone` and an icon-only square form; ModalSheet is taller for 114 rows). The
rest are this module's own: `AyahSurface`, `MetaChip`, `RefField`, `SearchLine`,
`SurahPicker`.

The chrome is Dekho's header band — a mosque glyph, `DEEN / QURAN · RECITATION`,
and the three rooms as chips on the right. The chips use `primary`, not
`selected`, which is the one place this module reads omakade's vocabulary
loosely: `selected` is a 0.12 wash over 0.045, enough to mark one chip in a
filter row and not enough to say which of three rooms you are standing in.

### Six things that had to be found by running it

- **`SearchField` is now a `QtQuick.Controls` type.** Qt ships one, and an
  explicit module import outranks the implicit directory import — so in any file
  that also imports QtQuick.Controls, a local `SearchField.qml` is silently
  shadowed and every custom property on it fails with *"Cannot assign to
  non-existent property"*, which reads as a typo and is not one. Ours is
  `SearchLine.qml`. **Dekho's copy is still called `SearchField` and is only
  safe because `LibraryScreen.qml` happens not to import QtQuick.Controls.**
- **`anchors.centerIn` silently ignores `horizontalCenterOffset`.** Cost a
  build to notice. Explicit `x`/`y` instead.
- **A Positioner's `childrenRect.width` is always its own width**, because the
  `Repeater` is a zero-sized child sitting at x=0 and the union of children's
  rects therefore always reaches the left edge. `implicitWidth` is the content
  width. This is what centres a one-line ayah in a card twice its width.
- **`lineHeight: 1.7` was measuring the wrong thing.** It was set to keep the
  Uthmani marks off the line above — but Noto Naskh Arabic already declares a
  line box of roughly *twice* its em for exactly those marks, so 1.7 on top of
  it put 3.4 em between the wrapped lines of Al-Baqarah, which reads as two
  separate ayat. It is 1.15 now, and nothing collides.
- **`qs ipc call deen recite <ref>` never set the view.** Called while the hub
  sat on the reader it changed the ayah behind a screen that does not show one,
  and the pedal then recorded against an invisible Recite screen.
- **The transliterations spell long vowels out** — `Ar-Rahmaan`, `Al-Ikhlaas`,
  `As-Saaffaat` — so a substring search for `rahman` found nothing in a list
  containing Ar-Rahmaan. The picker's fold collapses runs of the same letter on
  both sides, and strips Arabic harakat for the same reason.

### The reader is two columns

Arabic is right-aligned and its translation is not, so stacking them in one
980 px column put the two lines at opposite ends of the page with a thousand
pixels of nothing between them — the user's *"can we make better design for
this"*. Side by side, that space becomes the gutter, and each ayah gets a
resting tint so the leftover reads as padding inside a block rather than as a
hole. It folds back to stacked below 620 px of content, because two columns of
two words each is worse than one column of four.

English joined Bangla there: the column had the room, and the screen exists for
someone who cannot yet read the first line.

### The surah picker

111 presses to reach An-Nas, and nothing on the page that looked like it would
answer "take me to Ar-Rahman". **The title is now the browse button** — one
control to find, and it is the thing already telling you where you are. The
sheet opens centred on the surah you are reading, searches name/meaning/Arabic/
number, and Enter takes the top match.

## 13. Type scale: the measurement, and what it corrected

The complaint was "fonts are too small on the 32-inch NUC and the 27-inch mini".
Two things in the earlier handoff turned out to be wrong, and one thing nobody
had measured turned out to be the whole problem.

**The 2.1 boost ceiling is not the binding constraint.** The NUC's raw boost is
2.116. The clamp costs 0.8%. Raising or removing it buys nothing visible.

**The hub was never the small thing.** Measured end to end, at type(30):

| | boost | device px | mm | at | apparent |
|---|---|---|---|---|---|
| MacBook, scale 1.5 | 1.04 | 46.6 | 5.21 | 50 cm | 35.8′ |
| NUC, scale 1 | 2.10 | 63.0 | 11.51 | 75 cm | **52.8′ (+47%)** |
| Mini, scale 1.1 | 1.93 | 63.7 | 9.93 | 65 cm | **52.5′ (+47%)** |

The hub scales with its window. **Nothing else in the shell scales with
anything**, and that is the actual gap. The base 12 px UI:

| | mm | at | apparent |
|---|---|---|---|
| MacBook | 2.01 | 50 cm | 13.8′ |
| NUC | 2.19 | 75 cm | **10.0′ (−27%)** |
| Mini | 2.06 | 65 cm | **10.9′ (−21%)** |

All three panels are within 10% of each other **in millimetres** and a quarter
apart in what the eye receives, because a 32" monitor sits half a metre further
away than a laptop. **Density is the wrong invariant for a desk; arc-minutes is
the right one.** Matching the MacBook wants scale 1.38 on the NUC and 1.33 on
the mini.

Chosen, by the user, with the numbers in front of them: **DP-3 → 1.5**
(2560×1440 logical, +9% versus the MacBook, giving up a third of the rows and
columns) and **HDMI-A-1 → 1.3333333** (2880×1620, within 3%). Four thirds
divides 3840 and 2160 exactly; `1.333` would give 2880.7×1620.4.

**The hub is untouched and does not move either way.** Its `boost` comes from
the window's *logical* size, so raising the output scale multiplies the device
pixels and divides boost by the same factor: the ayah stays at ~63 device px at
scale 1, 1.25 or 1.5. The ceiling stays at 2.1 — after the scale change nothing
reaches it, so raising it would be a number with no behaviour.

The viewing distances are estimates and are the only soft number in any of this.
If a monitor moves, redo the sum. `physical_size` from `niri msg --json outputs`
is trustworthy on both machines (700×390 mm and 286×179, checked against the
stated diagonals) — the Wayland "compositors report nonsense for physical size"
worry did not materialise here.

## 14. Salat: dropped, 2026-09-05

The user's words: *"Let's skip Salat because I will learn it from books."*

**Dropped, not deferred, and nobody should propose it again.** It is the one
screen in this plan where the tool could not beat the alternative. Everything
else here does something a book cannot — score a recitation, schedule a review,
sound a word you cannot read. A salat walkthrough is a book rendered on a
screen, and the book is better: it is already verified, it does not need the
laptop open, and its author can be asked.

### What the search found first, since it should not be redone

There is **no open structured dataset of salah steps**, in any madhhab. Searched
twice. Prayer-*times* libraries are abundant; a step machine (niyyah → takbir →
qiyam → ruku → i'tidal → sujud → jalsa → tashahhud → salam) with per-step
Arabic, transliteration and rakah branching does not exist as open data. It gets
authored, not downloaded — which is exactly the cost this decision declines to
pay.

Prose sources do exist and were assessed:

- [Method of Hanafi Salah](https://islamqa.org/hanafi/daruliftaa-birmingham/135565/method-of-hanafi-salah/),
  Darul Ifta Birmingham — 32 steps in order, answered by Molana Eunus Ali,
  checked by Mufti Mohammed Tosir Miah, citing *Mukhtasar al-Quduri* and *Radd
  al-Muhtar*. Arabic and transliteration on nearly every dhikr; **no English
  translation of them**.
- Dawat-e-Islami's *Method of Salah (Hanafi)* — a full manual, but a Barelvi
  organisation, which is a lineage question and not a technical one.
- Tariq Mahmood Nishter's *A Muslim's Guide to Prayer*, on *Munyat al-Musalli*,
  *Nur al-Idah* and *al-Quduri*.
- Bangla: qnabangla, sunnahit. Readable, weakly attributed.

### The design that was going to be built, if this is ever reopened

Two independent sources that had to agree, so the §7 rule became a mechanism
rather than a promise:

| what | from | checked by |
|---|---|---|
| Fatiha and the surah after it | Tanzil, already installed | already verified |
| the Arabic of each dhikr | a hadith corpus, by book + number | matching the manual's text |
| order, rakah counts, postures, fiqh | one Hanafi manual | a person, once |

Any step where the two disagreed, or whose Arabic was not found in the corpus,
would render as **unverified and say so** rather than render silently. The
hadith side is real and available —
[AhmedBaset/hadith-json](https://github.com/AhmedBaset/hadith-json), 50,884
hadiths from 17 books including the nine, Arabic and English, per-book and
per-chapter, and it asks callers to pin a tag, which is the discipline
`scripts/fetch-data` already applies to Tanzil.

The point of writing this down is that the *architecture* was never the blocker
and never in doubt. The blocker was that a person has to stand behind the
content, and the user has decided that person is an author of a book they are
reading rather than anything in this repo. That is the right answer.

## 15. Continuous recitation on the Read screen, 2026-09-05

User's ask: *"add a play button in read page and if I click play, whole surah
will be played with highlighting and scrolling"*.

**A queue of references and an index into it, not a playlist handed to mpv.**
One `mpv file1 file2 …` would play a surah gaplessly and tell the shell nothing
about where it had got to — and knowing which ayah is sounding is the entire
point, because it is what highlights the line and scrolls the page. One process
per ayah costs a few hundred milliseconds between them, which is a pause a
recitation has anyway.

**The Basmala goes first**, from `deen`'s own `basmala` field rather than a rule
here — which is also why the line is empty on Al-Fatiha (its opening ayah *is*
the Basmala, so it is already in the queue) and on At-Tawbah (which has none).

### Prefetch is not a nicety, and here is the measurement

```
deen audio 112:1   cached     0.001 s
deen audio 112:2   uncached   1.237 s
```

Without prefetching the next ayah while the current one plays, **every gap on a
first listen is 1.2 seconds** of silence. `deen audio` already caches and
answers a path, so ignoring the path is the whole of the prefetch.

### Four things the chaining needs to get right

- **The index is cleared before the process is killed.** `onExited` advances the
  queue, and an empty index is the only thing that distinguishes "you pressed
  Stop" from "that ayah finished". Get the order wrong and Stop plays the next
  ayah.
- **A superseded process does not get to clear its successor's highlight.**
  Tapping a word during a recitation kills the running mpv and starts another;
  the corpse's `onExited` arrives afterwards and would blank `playing`. It
  returns early if `audioProc.running` is true again.
- **Three consecutive non-zero exits stop it.** A surah whose audio will not
  fetch would otherwise spin through 286 ayat in about a second.
- **Changing surah stops playback**, or a queue of references from the old surah
  goes on reciting underneath the new one's text.

### The page follows the recitation

`positionViewAtIndex` sets `contentY` outright, and a page that teleports every
eight seconds is worse company than one that does not move. So: let it do the
arithmetic, take the answer, put the page back, and animate to it. It stands
down while the list is being dragged or flicked — a reader who has scrolled away
is reading something else, and a list that hauls itself back is arguing — and a
theme shipping `duration = 0` gets the jump, like everything else in the module.

**Tapping an ayah number means two things by design:** "just this one" when
nothing is playing, and "carry on from here" when a surah is. The one-off tap is
what the reader was built around; the jump is what you want the moment there is
a recitation to move.

### A testing gotcha that cost real time

**A synthetic keypress can be processed *after* an IPC call sent later.**
`wtype -k Return` puts a key in the compositor's queue; `qs ipc call deen read
36` goes through Qt's event loop too, and if the shell is busy the IPC can land
first — so a test that presses Play and then immediately switches surah can end
up starting playback on the *new* surah and looking like a stuck state. It is
not a bug in the module; it is a bug in the test. Put a real sleep between a
keypress and the next IPC call, and verify against `pgrep mpv` rather than
against the button's label alone.

## 16. Distribution, 2026-09-05

The repo exists: **github.com/saifulapm/deen**, public, MIT, mirroring dekho.
Public is not a preference — `run_after_49-deen.sh` clones it over anonymous
https, so private would need auth on every machine to install a binary whose
whole point is that it holds no key.

Three gaps closed, and only one of them was the missing repo:

1. **The vicinae entry was authored but never applied.** `shell-deen.sh` had sat
   in the chezmoi source since the hub shipped while `shell-dekho.sh` was
   deployed back in August — no `chezmoi apply` had run in between. Applied on
   its own (`chezmoi apply <target>`) rather than by a full apply, which would
   have re-run sixty run-scripts to place one file. It now answers "Islamic Hub"
   in the launcher, beside "Movies & TV".
2. **`update-all` knew about dekho and not deen.** Same `update_src` lane:
   advance the checkout, delete the binary, let the guarded `run_after` rebuild
   on the apply that follows. The text and the model are deliberately *not* in
   that lane — they are fetched once and guarded on their own files, because the
   Quran does not change.
3. **The repo.** Created with `gh`, pushed, and the anonymous clone verified
   against the exact URL the installer uses.

### Verified against a fresh machine, not asserted

`run_after_49-deen.sh` had never successfully run anywhere but this laptop,
because there was nothing to clone. It was run against an empty `HOME` with a
clean environment:

| step | result |
|---|---|
| clone from the new repo | ok |
| `scripts/fetch-data` → `quran.json` | 5.2 MB |
| model download + header patch | `n_text_ctx 1024 → 448`, applied |
| `cargo build --release` | ok |
| the built binary against the fetched text | 114 surahs, 4 words in Al-Ikhlas 1, 3 tajweed spans on 1:2 |

And the invariant that matters most, because it is what makes the three
silent-failure modes in §9 impossible to hit on one machine and not another:

```
sha256  quran.json                 →  identical on both
sha256  ggml-quran-base-q8.bin     →  identical on both
```

**A fresh machine gets byte-identical text and a byte-identical patched model.**
The fetch is deterministic, so the tajweed offsets, the word-audio numbering and
the Basmala cut are the same everywhere or nowhere.

One note for whoever runs this next: with `env -i` the build fails with *"rustup
could not choose a version of cargo"* — that is the sandbox having no rustup
default, not a bug in the script. On a real machine `run_after_03-dev-toolchain`
has already set one, and the script's own dependency check is what handles the
case where it has not.

### The random-verse script is gone (§1's prediction, collected)

`quran-verse.sh` was retired on 2026-09-05. §1 called it from the start — it
survived only until the Mushaf screen replaced it, and the Read screen now draws
any surah word by word, tajweed coloured, from local data with no network call
at all, where the script fetched one random ayah from alquran.cloud and had to
hand-drive `fribidi --reordernsm` to get it the right way round.

**It needed its own removal script, and the reason is worth keeping.**
`run_after_50-stale-links.sh` sweeps *dangling symlinks pointing into the repo*
— deliberately exact. Vicinae scripts carry the `executable_` prefix and chezmoi
deploys them as **regular files**, so a deleted source leaves a real 2 KB script
behind that no predicate about links will ever match. It would have gone on
offering "Quran: Random Verse" in the launcher for ever.
`run_after_51-quran-verse-remove.sh` guards on the file containing our own
`@vicinae.title` marker, which is the regular-file equivalent of run_after_41's
`-L && ! -e` care: anything else at that path is a deliberate replacement.

**Removing it orphaned three justifications**, all updated rather than left
lying: `packages/manifest.toml` claimed `fribidi` *solely* for this script,
`templates/foot.ini.tmpl` cited it, and so did the Arabic rule in
`fontconfig/conf.d/50-qshell.conf`. The fribidi claim is **kept**, with an
honest new reason: `deen` is a terminal program whose documented usage prints
Arabic (`deen api ayah 1:6 | jq -r .ayah.ar`), and without fribidi that arrives
letter-isolated and in reverse.

## 17. The Duas screen, 2026-09-05

The last screen from §5 that was never built and never dropped. Daily adhkar,
and the one screen whose whole difficulty was §4c's rule rather than any code:
**where do the bytes come from, and can the person reading them check?**

### The two candidates in the handoff both failed, and the search found better

| | verdict |
|---|---|
| `ahmedeltaher/azan-mcp` (`adhkar.json`, `duas.json`) | **Rejected.** 20 adhkar — 10 morning, 10 evening, and the evening set is the morning set with identical citations — plus 19 duas over 15 topics. Its `confidence` field is the attractive part and is the disqualifying one: the README defines `high` = Bukhari/Muslim, `medium` = Sunan, so it is *which book is named* wearing a grading's clothes. A weak narration in Abu Dawud reads as though somebody graded it. One "initial release" commit, no compilation script, no provenance. |
| `AhmedBaset/hadith-json` | **Not this screen's dataset.** A corpus (50,884 hadiths, 17 books), not an adhkar collection — choosing which hadiths *are* the morning adhkar would be this repo authoring religious content, which is exactly what the rule forbids. It fails as an automatic verifier too: Hisn al-Muslim cites volume/page (260 of 268) and not hadith numbers (32 of 268), so number-matching would cover about 12%. Also has no LICENSE file at all. |
| **sunnah.com/hisn** + `majmoo-io/hisnu-al-muslim-data` | **Chosen.** One page carries all of it, aligned by construction. |

**Hisn al-Muslim is structured data — as HTML, on sunnah.com, not as the JSON
everyone points at.** One page holds 268 duas in 132 chapters, each with a
citable id (`Hisn al-Muslim 27`, permalink `/hisn:27`), Arabic, transliteration,
English, and the book's own reference footnote. Coverage, measured: english
268/268, reference **267/268** (the one gap is literally `ibid.`), transliteration
255/268, arabic 268/268 once the parser also reads `arabic_hadith_full` — nine
items put the Arabic straight in the div instead of the inner span.

The JSON datasets that exist are all *worse copies of this page*: one keeps the
Arabic and the footnotes and drops the translation, another keeps ar/en/tr and
drops every reference.

### The install refuses rather than shipping a half-right book

`scripts/fetch-duas` fetches sunnah.com's page **and** majmoo-io's archive of
that same page, pinned to a commit, parses both with the same code, and installs
only if every field of all 268 duas matches. This is §14's two-source design,
which Salat never got to use, applied where it costs one extra HTTP GET.

It is not theatre. Measured before writing it: the live page and the ~5-month-old
archive parse to **268 byte-identical rows**. And majmoo's two independent Arabic
scrapes (sunnah.com and majmoo.io) agree on **266/268** — the 12 raw mismatches
are all word-spacing artefacts plus two hamza-carrier variants (يَؤُودُهُ /
يَئُودُهُ) and one extra word.

One note for whoever runs it: **sunnah.com answers 403 to a bare curl and 200 to
a browser User-Agent.** That is a rate-limiting rule on a public page, not a
paywall — but it means the fetch carries a UA string, and if that stops working
the archive alone is not enough to install, by design.

### Counts and audio come from a third dataset that is never a source of content

`YousefAsalya/Islamic-Pro-azkar-API` (MIT) has ar/en/tr, a repeat count and an
mp3 per entry, and **no references at all** — so it supplies "say this three
times" and a sound, and nothing that is asserted.

**Joined on the normalised Arabic, never on position.** The two agree on the 132
chapters and disagree on how many entries some hold (chapter 27 is 25 items in
the book and 24 there), so a positional join would hand a dua its neighbour's
repeat count — silently, which is the failure mode §9 already got burned by.
Exact match reaches 217, difflib ≥ 0.90 reaches 250 of 268.

The thing that makes the join trustworthy is not the ratio: **for all 250, the
matched audio file is the dua's own number in the book.** Two independent routes
— text and numbering — agreeing. The other 18 render with no count and no play
button rather than with a guessed one, and `deen audio dua:4` says so.

### What the screen is

Third room in the header, `qs ipc call deen duas`, and the same anatomy as the
reader so the hub stays one place: ◀ ▶, the title as the browse button, a Play
that recites the whole chapter, chips for the source. It opens on chapter 27,
"In the morning and evening", because that is what daily adhkar means.

**Every card carries the footnote**, full width, never elided, under both
columns — a citation you have to hover to finish reading is a citation being
hidden. Above it: the book's number as the badge (and the play button when there
is audio), the transliteration in the brighter ink because it is the whole point
for someone who cannot yet read the line beside it, then the English, then the
Arabic on the right.

Three things fell out of building it:

- **`playSurah` became `playList`.** A surah and a chapter of adhkar are the
  same problem once they are a list of references to fetch and sound in order,
  so the queue, the prefetch, the three-failure stop and the follow-the-page
  scroll are one implementation. The duas with no audio are left *out* of the
  queue rather than left in to fail — two of them in a chapter would trip the
  three-failure stop halfway through for a reason nobody could see.
- **The pedal now shows the Recite screen before it records.** It was the same
  bug §12 fixed for `reciteAyah`: pressed from the reader it started a recording
  against a screen that is not on screen. A fourth room made it worth fixing
  rather than working around.
- **A second picker, not a reused one.** `SurahPicker` folds doubled letters so
  `rahman` reaches Ar-Rahmaan; on English chapter titles that same fold would
  make "sleeping" and "seeping" the same word. `DuaPicker` searches the English
  title, the Arabic title and the number, and nothing else.

### What it does not have

**No Bangla.** Searched: there is no open Bangla Hisnul Muslim dataset, and the
IslamHouse Bengali repo that turns up is an empty API-docs stub. The screen
shows transliteration and English, which is the honest shape of the data — and
the transliteration is the part that matters most for saying a dua you cannot
yet read. If a Bangla source ever turns up it aligns to the 268 by the same
two-source rule, and whatever does not align stays English-only.

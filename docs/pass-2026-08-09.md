# pass — password manager setup (2026-08-09)

## The decision

`pass` over KeePassXC and Bitwarden, chosen for minimalism (user decision
2026-08-09). ~300 lines of bash over `gpg` + `git`: one encrypted file per
entry, the store its own git repo.

The deciding argument was sync. A KeePassXC `.kdbx` is a single binary blob,
so two devices editing inside one sync window produce a whole-database
conflict that needs a manual merge. `pass` has no analogue — entries are
separate files and git resolves them per-file, which is a problem this setup
already knows how to handle.

**Passkeys are explicitly out of scope.** They live in iCloud Keychain on the
iPhone and reach Chromium here over the WebAuthn hybrid/QR transport, which
needs only Bluetooth (present and working on this machine). `pass` is for
passwords only. Nothing below tries to make it do passkeys.

Accepted costs, recorded so they are not rediscovered as bugs:

1. **No save prompt.** Browserpass only reads. Every new account is a
   `pass insert` in a terminal.
2. **Filenames are metadata.** GPG encrypts contents, not names. Anyone with
   the repo learns every service you hold an account with, even without the
   passphrase. This is why the store is private and separate (below).
3. **The GPG key is a single point of failure.** Lose it with no backup and
   every entry is unrecoverable. There is no vendor reset.

## Store location — the one rule

The store is a **separate private repo**: `github.com/saifulapm/password-store`
(created 2026-08-09, verified PRIVATE), cloned to `~/.password-store`.

It must **never** be moved into `~/.dotfiles`. That repo is PUBLIC (verified
2026-08-09 via `gh repo view`). Because of cost #2 above, committing the store
there would publish a complete index of every service in use — the passwords
would stay encrypted and it would still be a serious leak.

`pinentry-qt` is **not** cosmetic. Fedora's base `pinentry` is curses-only, and
browserpass runs under Chromium with no controlling tty — without a graphical
pinentry, every browser autofill blocks on a prompt that cannot be drawn and
then times out with nothing on screen. `pinentry-qt` rather than
`pinentry-gnome3` because this is niri: gnome3's prompter degrades back to
curses when no GNOME session answers.

Two notes from doing it (2026-08-09):

- The shell redirect in `gpg --export-secret-keys ... > file.asc` writes with
  the default umask, so the export landed **0644 — world-readable**, while the
  revocation cert gpg wrote itself came out 0600. Corrected by hand. Worth
  a `chmod 600` immediately after any future export.
- `$HOME` is **btrfs**, so `shred` on these files is theatre: copy-on-write
  plus SSD wear-levelling mean the old extents are not necessarily overwritten.
  Plain `rm` is honest, and what actually protects the export is that it is
  passphrase-encrypted (verified: 8 protection markers, not a bare key).

## Interactive steps — these need your hands

Steps 1 and 2 cannot be automated: one needs sudo, the other needs a
passphrase only you should know. Step 3 needs the passphrase too.

### 1. Install the packages

```
chezmoi apply
```

Must be run **from a terminal**. `run_before_00-install-packages.sh` skips
loudly when it cannot sudo, so a background apply installs nothing.

This also rewrites `~/.gnupg/gpg-agent.conf` to point at `pinentry-qt` (until
then the template falls back to `/usr/bin/pinentry`, deliberately — an agent
pointed at a missing binary fails operations rather than falling back, which
would break gpg for everything, not just pass).

### 2. Generate the key — RSA 4096, NOT ed25519

```
gpg --full-generate-key
```

Answer: `(1) RSA and RSA` → `4096` → `0` (no expiry) → your name/email →
a strong passphrase.

**Use RSA even though ed25519 is the modern default.** Pass for iOS runs
GopenPGP, where Curve25519 works in principle but has rough edges — notably
when the master secret key is stripped and only subkeys are exported.
RSA 4096 is the best-tested path through that client. Decryption speed is
irrelevant for payloads this small.

For the same reason, **keep the full master secret key**. Do not do the
offline-master / subkey-only export dance; it is a known crash source there.

No expiry (`0`) because an expired key on a password store means re-encrypting
every entry. Nothing else here depends on rotation.

Then note the key ID:

```
gpg --list-secret-keys --keyid-format=long
```

### 3. Back it up — before you store a single password

Do this step **first**, while the store is empty and the cost of getting it
wrong is zero.

```
gpg --export-secret-keys --armor <KEYID> > gpg-secret-<KEYID>.asc
gpg --gen-revoke --armor --output gpg-revoke-<KEYID>.asc <KEYID>
```

**Removable media is NOT a requirement.** An earlier draft of this document
said "offline media, a USB stick or printed", which was reflex rather than
reasoning. The export is passphrase-encrypted, so its confidentiality is set
by the passphrase, not by the storage location. Only two rules actually bind:

1. **At least one copy that is not on this laptop.** This is an availability
   problem — disk failure, theft, a botched reinstall — not a secrecy one.
2. **The storage must not require a password that lives only in `pass`.**
   That circularity is the trap that actually catches people: the backup you
   cannot reach precisely when you need it.

Two places it still must never go, and neither is about the storage medium:

- The password store itself — you would need the key to read the key.
- `~/.dotfiles` — that repo is PUBLIC.

**Chosen 2026-08-09: iCloud Drive**, at `iCloud:GPG-Backup/` via the existing
rclone remote. It satisfies both rules — the Apple ID credentials live in
iCloud Keychain, wholly independent of `pass` — and it is not a new category
of trust, since `.ssh` was already stored there. A visible folder rather than
a dotfolder on purpose: the iOS Files app hides dotfolders, and step 6 needs
to reach this same key from the phone.

Verified by round trip, not just by upload: `rclone check` could only compare
sizes (the iclouddrive backend exposes no hash), so the files were downloaded
again and confirmed byte-identical by sha256, with the copy re-parsed to show
2 secret key packets.

If your Apple account were breached the attacker gets an encrypted blob and
still needs the passphrase — which is the entire reason this is acceptable,
and the reason the passphrase must be strong.

**The GPG passphrase is now the one password you must remember.** It cannot
live in `pass`, and it is not in iCloud. Memorise it, or write it on paper
kept apart from everything above. Everything else in this setup exists to
mean you never remember another one.

### 4. Initialise the store — DONE 2026-08-09

Recorded for the next machine; already applied on this one.

```
pass init 40661486CE0B62A46BB25A3FD0B482713583CC5B
pass git init
git -C ~/.password-store branch -M main
pass git remote add origin git@github.com:saifulapm/password-store.git
pass git push -u origin main
```

**Laptop pushes over SSH, the phone pulls over HTTPS.** Same repo, two
transports, independent of each other. SSH here because the key that already
pushes this dotfiles repo works with no new credential helper — there is no
`credential.helper` configured on this machine, so an HTTPS push would have
prompted for a username and password. HTTPS on the phone is not a preference
but a workaround for a passforios limitation (see below).

Encryption was verified end to end with a throwaway entry: the resulting
`.gpg` was confirmed encrypted to subkey `0D703A9414F953D8` (the `[E]`
subkey, which is what pass uses), contained no readable plaintext, and was
then removed. The store's git history was squashed to a single clean commit
before the first push — worth knowing as a habit, because a password store's
history retains every superseded encrypted blob forever.

### 5. Browserpass extension

Install from the Chrome Web Store:
<https://chromewebstore.google.com/detail/browserpass/naepdomgkenhinolocfifgehidddafch>

Deliberately not repo-bundled via `--load-extension` like the omarchy pair —
the Web Store copy keeps auto-updating (3.12.0 as of 2026-05).

The native host is already registered by `run_after_21` once the package is
installed. If the extension reports **"host not found"**, re-run:

```
bash ~/.dotfiles/home/.chezmoiscripts/run_after_21-chromium-extensions.sh
```

then restart Chromium. Use `Ctrl+Shift+L` → filter by domain → Enter.

### 6. iPhone

Install **Pass — Password Store** from the App Store (mssun/passforios). It
does git sync, GPG, TOTP, and iOS AutoFill.

- **Sync over HTTPS with a GitHub PAT — not SSH.** passforios has documented
  ed25519 SSH auth failures ("Unable to extract public key from private key")
  in its libgit2/libssh2 transport. That is a transport-layer limitation, so
  no PGP-side change fixes it. Create a fine-grained PAT scoped to
  `password-store` only.
- **Import the secret key.** The phone needs the *secret* key to decrypt.
  Getting it there: `bin/dufs-serve` (the bar's dufs widget) already serves
  `$HOME` over LAN and is the least-bad transfer path — but it is **plain HTTP
  with a fixed password**, so switch it off the moment the transfer finishes.
  The armored export is passphrase-encrypted, which is what makes this
  tolerable rather than reckless.

## Fresh install — two phases

```sh
# phase 1 — from a TTY. Public repo, no credentials.
cd ~ && sh -c "$(curl -fsLS get.chezmoi.io)" -- init --apply --source ~/.dotfiles https://github.com/saifulapm/dotfiles.git

# reboot -> autologin lands you in the niri session

# phase 2 — in the desktop session
rclone config          # iCloud ONLY — Apple 2FA, the one unavoidable login
secrets-restore        # Dropbox, SSH, GPG, store, age key, licence
tailscale up           # one browser click
```

Plus the Browserpass extension from the Web Store, and Chromium restarted.

**The root of the restore is iCloud, and that is deliberate.** The GPG key
lives at `iCloud:GPG-Backup/` and the SSH keys at `iCloud:.ssh/` — neither is
in this repo, because this repo is public. Reaching iCloud needs the Apple ID,
which lives in iCloud Keychain on the iPhone and never passes through `pass`,
so the chain cannot deadlock.

### Why two phases and not one

The tempting simplification is to configure rclone first and let a single
`chezmoi apply` do everything. It does not work, for a measured reason
(2026-08-09):

- `pinentry-qt` with no `DISPLAY`/`WAYLAND_DISPLAY` does not fall back to a
  terminal prompt. It **aborts** — SIGABRT, core dumped.
- `gpg --import` of a passphrase-protected key with no usable pinentry then
  **exits 0 having imported nothing**. A silent success that leaves you with
  no key.

Phase 1 runs from a TTY, so any GPG import folded into it would appear to
succeed and quietly do nothing. Phase 2 runs after autologin, where pinentry
can actually draw. `bin/secrets-restore` refuses to run without a graphical
session rather than reproduce that failure.

Configuring rclone before chezmoi does not help either: rclone itself arrives
via `packages/manifest.toml` in phase 1, so doing it first means installing
rclone by hand — adding a step rather than removing one.

### What `secrets-restore` does

Idempotent; every step detects prior work and skips. Ordered by dependency —
SSH first, because the store clone authenticates with it.

| Step | Source |
|---|---|
| Dropbox rclone remote | `iCloud:rclone/dropbox.conf` |
| SSH keys + `config`, permissions asserted | `iCloud:.ssh/` |
| GPG key imported **and ownertrust set** | `iCloud:GPG-Backup/` |
| `~/.password-store` cloned | `git@github.com:saifulapm/password-store.git` |
| chezmoi age key (if one is ever used) | `iCloud:chezmoi/key.txt` |
| intelephense licence | `iCloud:.dotfiles/config/zed/settings.json` |

### Credentials: what is restored and what is not

**Dropbox is restored** because its `[Dropbox]` section is an OAuth
`refresh_token` and nothing else — no password — and rclone renews the access
token itself, so one backup never goes stale. That removes the second browser
login from phase 2, leaving iCloud as the only interactive one.

**Only the `[Dropbox]` section is backed up, never the whole `rclone.conf`.**
The `[iCloud]` section stores the Apple ID password under rclone's "obscure",
which is *reversible* — `rclone reveal` prints it in clear (confirmed
2026-08-09). That makes `~/.config/rclone/rclone.conf` exactly as sensitive as
the Apple ID password itself, which is worth remembering against the dufs
audit note that a password-holder can fetch any `$HOME` path by direct URL.
It is also the bootstrap credential, so it must be typed by hand regardless.

**Tailscale is deliberately not automated.** Auth keys cap at 90 days —
"reusable" raises the registration count, not the lifetime — so a stored key
would be expired at precisely the moment a reinstall needs it. The long-lived
alternative is an OAuth client, which requires device tags and is aimed at
servers and CI rather than a laptop. `tailscale up` is one browser click,
which is cheaper than maintaining either. (Backing up the root-owned
`/var/lib/tailscale/tailscaled.state` would also preserve node identity, at
the cost of root access on both ends and version fragility.)

Two behaviours worth knowing, both from measurement rather than assumption:

**Ownertrust is set explicitly, and it is not optional.** A generated key
carries ownertrust `u`, but that same key exported and imported into a virgin
keyring lands at `-`, and every encryption then fails with *"There is no
assurance this key belongs to the named user" → "Unusable public key"*.
`pass insert` dies with that and nothing explains why. The script uses
`gpg --import-ownertrust` (one scriptable line) rather than the interactive
`gpg --edit-key … trust` menu, and reads the fingerprint out of the key file
itself rather than hardcoding it, so a future key rotation cannot silently
invalidate it.

**The import is verified by counting secret keys, not by exit status**, for
the reason above: `gpg --import` returns 0 even when it imported nothing.

`~/.ssh` permissions are reasserted on every run, not just on restore, because
rclone writes with the default umask and ssh silently refuses any private key
it considers group- or world-readable.

### Verify

```sh
pass show github.com
```

The real end-to-end proof — it exercises the key, the trust, the agent and the
store together.

## Entry format

Browserpass and Pass for iOS share one convention, so write entries this way
or autofill will find the password but not the username:

```
correct-horse-battery-staple
login: saifulapm@gmail.com
url: https://github.com
```

Password on line 1. Username on a line starting `login:`, `username:` or
`user:`.

## Daily use

```
pass                      # tree of everything
pass show github.com      # print
pass -c github.com        # copy (clears after 45 s)
pass insert site.com      # new entry
pass generate site.com 32 # generate + store
pass edit site.com
pass git push             # sync
```

Fish completions ship with the package.

`chezmoi` can read from the store directly (`pass` template function), which
is the intended fix for the secrets this repo currently cannot commit —
`rclone.conf`, the intelephense key.

# YouTube in the launcher: a yeetube port — 2026-09-06

Type a song title into vicinae, press Enter on **Search on YouTube**, pick
from real results, watch it in mpv. That is
[yeetube](https://thanosapollo.org/projects/yeetube/)'s whole loop, which had
lived in Emacs, moved to the launcher that is already bound to a key.

## What landed

- **`bin/youtube`** — the engine. `search`, `channel`, `play`, `audio`,
  `download`. Prints JSON; works in a terminal with vicinae stopped.
- **`vicinae/youtube/`** — the extension: two commands (`search`, `library`),
  built per machine by `run_after_53-vicinae-extensions.sh` into
  `~/.local/share/vicinae/extensions/youtube/`.
- **`vicinae.service`** — dropped `--no-extension-runtime`.
- **`overrides.json`** — `fallbacks: ["@saiful/youtube:search"]`, which is what
  makes an arbitrary typed phrase offer the command at all.
- **`bin/chromium-ytdlp-host`** — gained `--audio` on its `--download` worker,
  so downloads reuse the OSD progress bar and completion toast rather than
  growing a second copy of them.

## 1. Search is yt-dlp, not a scraper

yeetube parses `ytInitialData` out of the results page by hand — 22 KB of
`yeetube-scraper.el` that breaks whenever YouTube reshapes its JSON. yt-dlp is
already installed, already carries that maintenance burden for
[[pkg]] cliamp and [[tool]] dekho, and is already kept fresh for them.

The query is a **results URL with an `&sp=` filter code**, not `ytsearch20:`.
`ytsearch:` can only return default relevance ordering of videos; the `sp`
parameter selects sort *and* type, and yt-dlp passes it through untouched.
Verified 2026-09-06, because "accepted" and "honoured" are different claims:

| filter | code | evidence it is honoured |
| --- | --- | --- |
| relevance | `CAASAhAB` | first hit for `music`: 4.0M views |
| upload date | `CAISAhAB` | reorders against relevance |
| view count | `CAMSAhAB` | same query, first hit: **699M** views |
| rating | `CAESAhAB` | — |
| live | `EgJAAQ%3D%3D` | every row `live_status: is_live` |
| playlists | `EgIQAw%3D%3D` | rows are `/playlist?list=…` |
| channels | `EgIQAg%3D%3D` | rows are `ie_key: YoutubeTab` channels |

`--flat-playlist`, so one request answers with title, channel, duration, view
count and a thumbnail for every hit. **2.3 s for 20 results, 3.8 s for 60**
(measured). Without it yt-dlp visits every watch page — a minute, for data the
search page already handed over.

### Search fails intermittently, and the cause is the DNS filter

Searches returned zero rows several times during the build, and the identical
query a moment later returned twenty. Thumbnails did the same — 3 of 20
thumbnail URLs failed to connect at all while the other 17 fetched with a
200. Both cleared up on their own.

**`dns-filter status` says `YouTube blocked`.** That is the family-wide
uBlockDNS category from `docs/dns-filter-toggles-2026-09-06.md`, and the
inconsistency is exactly what that document describes: several caches sit in
the chain, so a machine gets a filtered answer and an unfiltered one minutes
apart depending on which one replied. It is not this extension, and it is not
yt-dlp.

The practical consequence: **`dns-filter off youtube 2h` before a viewing
session**, which is what those toggles were built for. Ruled out along the
way — it is not a double-fetch. That theory came from seeing two
`bin/youtube search` processes and two `yt-dlp` processes in `ps` at once;
checking PPIDs showed the pairs are a bash command substitution and yt-dlp's
own fork, i.e. the normal shape of ONE search.

The empty view says results can just fail and offers **Try Again**, and a
failure that is not "no results" prints its actual message in the view rather
than only in a toast that fades.

## 2. Why a TypeScript extension, and what it costs

The launcher deliberately ran `--no-extension-runtime` since 2026-08-26 — no
resident node process, because every extension in use was native. Turning it
on costs **one node process, 75–95 MB RSS**, measured on this machine.

The zero-node alternative was a script command piping into `vicinae dmenu`,
which is what `bin/menu-select` already does. It was rejected on capability,
not taste: **dmenu takes plain newline-delimited text.** No per-row icon, no
subtitle, no accessories, no detail pane, no action panel, and no
search-as-you-type against a remote source — you would search once and then
filter what came back. The requested UI is a list of thumbnails with an action
panel, and that is an extension or it is nothing.

Node comes from mise (`~/.local/share/mise/shims/node`). Not pinned through
`VICINAE_NODE_BIN`: the server already finds it, and a variable naming a path
that a mise change could invalidate is a new way to break, not a guard.

## 3. Playback: both players are mpv, and one of them was not meant to be

**Video** — `app-run mpv`, i.e. its own transient unit under
`app-graphical.slice`, so playback outlives a launcher restart. Same reasoning
`bin/dekho-play` records at length. `--force-window=immediate`, because
resolving a stream takes seconds and a player that shows nothing reads as a
failed click.

**Audio** — was going to be `music <url>`, i.e. cliamp: it owns the MPRIS name
the bar and the XF86Audio\* keys talk to, and it queues instead of
interrupting. **It cannot.** Measured 2026-09-06 on both a music video and a
conference talk: cliamp sits at `No tracks loaded` with `ERR: resolving
youtube …` in its own UI — the URL never reaches a playlist. That is the
yt-dlp/cookies breakage [[pkg]] yt-dlp has recorded since 2026-08-18, not
something a wrapper can route around.

So audio is `mpv --no-video`. `mpv-mpris` is installed, so it still exports
`org.mpris.MediaPlayer2.mpv` and the bar and media keys drive it exactly as
they drive cliamp; only the queue and the library are lost. `cmd_audio` notes
the one-line swap back for when cliamp's YouTube resolution returns.

Audio runs under a **fixed unit name** (`youtube-audio.service`), stopping the
previous one first. A second video window beside the first is a normal thing
to want; two songs playing over each other never is.

### The player client pin is load-bearing

mpv's ytdl hook lets yt-dlp choose its own YouTube player client, and that
default does not work here. Unpinned, every video dies with:

```
[ytdl_hook] ERROR: Unable to download API page:
[SSL: TLSV1_ALERT_INTERNAL_ERROR] tlsv1 alert internal error
```

— while the same yt-dlp resolves the same URL fine on its own, so it is the
client, not the network. `--ytdl-raw-options=extractor-args=youtube:player_client=web_embedded`
fixes it. This is the **second** time this exact pin has been needed on this
machine: `[[tool]] dekho` records it for the trailer path on 2026-08-20, where
the symptom was a 403 instead of a TLS alert. When playback breaks, re-test
the pin before anything else.

Note the 403 is also *intermittent* on the media URL even with the pin — one
run failed and the next three succeeded on the same video.

## 4. Pagination appends, it does not regrow

YouTube re-runs the search for every page and does not return a stable
ordering. Two options:

- **Grow the limit and replace the list.** Self-consistent within one request,
  but the rows already on screen can reorder underneath the cursor.
- **Offset and append.** Rows never move. Measured overlap between two
  adjacent 10-row pages: **1 duplicate**, and no gaps observed.

Append won, and the duplicate is dropped by id when merging. Rows that are
already on screen not moving matters more than a perfectly disjoint page.

## 5. History and Watch Later live in vicinae, not a file

`LocalStorage`, which is namespaced per extension — verified by writing from
`search` and reading it back in `library`. A file under
`~/.local/state/qshell` would have needed a lock, a schema and a jq writer in
bash, to record something only the extension ever produces. History caps at
100 and replays move an entry rather than duplicating it.

The consequence, stated plainly: `youtube play` from a terminal does not
appear in the library. It is the extension's history, not the machine's.

## Not done

- **Cookies.** The one thing that would fix cliamp, YouTube Music playback and
  the intermittent 403s is a signed-in cookie jar — see the yt-dlp manifest
  entry, which measured that `07.04 + cookies` is the only combination that
  plays protected music content. Deliberately not added here: it puts an
  authenticated session into a scriptable path, and that is a decision to take
  on its own, not as a side effect of a launcher extension.
- **Subscriptions.** yeetube has RSS-based channel feeds. Nothing here reads
  them; `channel` browses on demand instead.
- **Resume position.** mpv's `--save-position-on-quit` would give it, at the
  cost of a watch-later directory that nothing prunes.

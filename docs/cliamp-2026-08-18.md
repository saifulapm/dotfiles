# cliamp replaces the homegrown music stack — 2026-08-18

Installed: **cliamp v1.63.2** (`cliamp-linux-arm64`, checksum-verified against the
release's own `checksums.txt`).

User ask: remove the bar's media/radio/music panel, set cliamp up properly for
YouTube Music, Spotify, radio and podcasts, check how omarchy does it, and make
sure we actually have everything cliamp offers.

---

## 1. What went, what stayed

**Removed** — `bin/radio` (324 lines), `bin/music` (90, rewritten), the bar's
`Media.qml` widget and `MediaPanel.qml`, the `"media"` entries in `shell.json`
and `Bar.qml`'s registry, `radio-stations`, `radio.fish`, and the five
`radio.*` menu rows.

**Deliberately KEPT: `shell/Services/Media.qml`.** This is the one judgement
call in the change and it is worth being explicit about. It looks like part of
"the media panel" and it is not — it is the MPRIS layer, and it has three
consumers that have nothing to do with the widget:

- every `XF86Audio*` bind in `config.kdl`, which calls `qs ipc call media …`
  rather than `playerctl`,
- the track-change OSD,
- the audio panel's active-stream highlight, which reads `activePlayer`
  straight off this service's preference ladder.

Deleting it would have silently broken the media keys for cliamp *and* for
browser tabs and mpv. Verified after the change: `qs ipc call media status`
returns cliamp's live metadata, and `playPause` round-trips.

## 2. How omarchy does it (checked, ref repo at `f32ebbd`)

Minimal, and there was nothing to port: `cliamp` in
`install/omarchy-base.packages`, a `SUPER+SHIFT+ALT+M` TUI bind in
`default/hypr/bindings/applications.lua`, a mention in `manual/21-tuis.md`, and
the package in the preinstall/remove lists. No config, no theming, no wrapper.

The interesting part is *why* they have it: our whole radio/music stack existed
because omarchy's music story used to be `pkg-add spotify`, which has no
aarch64 build. omarchy moved to cliamp for the same reason we now do.

## 3. The three-way config split

cliamp's config directory is not uniform, and getting this wrong would have put
credentials in a public repo.

| File | Managed how | Why |
|---|---|---|
| `radios.toml` | chezmoi symlink into the repo | cliamp only ever **reads** it (favourites go to `radio_favorites.toml`), so a station added is a diff you commit — same contract the old `radio-stations` had |
| `config.toml` | **seeded once** by `run_after_40-cliamp.sh`, then untouched | cliamp **rewrites** it |
| `themes/qshell.toml` | rendered by `bin/theme-apply` | tracks the desktop theme |

The `config.toml` hazard, verified in `config/config.go`: `Save()` runs on every
theme change and `cliamp setup` rewrites a whole `[provider]` block, both
through `fileutil.WriteFileAtomic` — write-temp-then-rename, which **replaces a
symlink with a regular file**. Chezmoi-managed, that would mean the repo goes
dirty every time you press `t`, `chezmoi apply` silently reverts a `cliamp
setup` run, and a Spotify token gets committed.

## 4. Theming is live

`templates/cliamp-theme.toml.tmpl` → `~/.config/cliamp/themes/qshell.toml`.
cliamp takes a theme's *name from the filename*, so it has to land as
`qshell.toml`; `config.toml` pins `theme = "qshell"`.

The poke works because `ipc.ThemeMsg`'s handler (`ui/model/update.go`) calls
`theme.LoadAll()` **before** applying — so re-sending the name it already has is
exactly what makes it re-read the file. Verified end to end: switched cliamp to
`dracula`, ran `theme-apply`, watched it snap back to `qshell` without a
restart.

Mapping: `accent`←`accent.accent`, `bright_fg`←`text.primary`,
`fg`←`text.muted`, and the spectrum's `green`/`yellow`/`red` ← the **ANSI**
trio rather than `accent.ok/warn/error`, because those three are a gradient
(the LED analyser ramp), not three statuses. All six are required —
`Theme.Validate()` rejects a partial palette outright rather than half-applying
it.

## 5. Why `bin/music` exists at all

Two things the bare binary cannot do:

1. **Outlive its terminal.** cliamp is a TUI; close the window and the music
   stops. The old `radio` dodged this by having no UI at all. `bin/music` holds
   the player in a detached tmux session on a **private server** (`-L cliamp`,
   own config) — not the `~/.tmux.conf` one, which runs `amx statusline` every
   second, rebinds the prefix and would draw a status bar across a player that
   already draws its own.
2. **Stay a singleton.** cliamp allows one instance (fixed IPC socket +
   `org.mpris.MediaPlayer2.cliamp`), and a second launch does **not** fail
   loudly — it starts anyway, silently loses MPRIS, and leaves a player the
   media keys and OSD cannot see. `new-session -A` makes a second launch attach
   to the first.

`RGB` in the tmux config is not optional: tmux advertises the capabilities of
`default-terminal`, not of the terminal it runs inside, so without
`terminal-features ",*:RGB"` the 24-bit qshell palette would be quantised to
256 colours.

### `url.load`, not `queue`

`music <url>` talks to cliamp's socket with `{"cmd":"url.load"}` (the `u` key's
code path) rather than the `cliamp queue` CLI verb. `queue` builds a track from
the URL's **filename**, so a YouTube link lands titled `watch`. `url.load` runs
it through yt-dlp / the RSS reader / the M3U parser first.

Measured difference — one podcast feed:

```
cliamp queue https://feed.syntax.fm/rss   → 1 row, titled "rss"
url.load     https://feed.syntax.fm/rss   → 1030 rows, real episode titles + durations
```

That is the podcast support, and it is why the socat dependency is worth it.

## 6. Gotchas worth not rediscovering

- **Upstream's `docs/cli.md` is stale.** It documents `--volume`, `--theme`.
  The v1.63.2 binary has `--vol` and `--start-theme`; `--volume` is rejected
  outright. Trust `cliamp --help`, not the docs.
- **`exec` cannot run a shell function.** `exec tm …` (where `tm()` wraps
  `tmux -L`) dies with `tm: not found`. Caught in testing; `bin/music` spells
  `tmux` out at that one call site.
- **`track.play` takes a track object, not an index**, and there is no
  jump-to-index verb — so there is no "drop what you are playing and play this"
  over IPC. `music <url>` appends when something is already playing.
- **cliamp's backend is ALSA.** `pipewire-alsa` is what makes it audible at
  all; without that bridge it plays in total silence with no error.
- **`cliamp status` exits non-zero when idle** — same contract as the old
  `radio status`, so it guards the menu rows unchanged.
- Chezmoi does **not** delete a file removed from source state; in symlink mode
  it leaves a dangling symlink. `run_after_41-radio-remove.sh` sweeps the two
  the old stack left (a dangling *completion* is not inert — fish sources that
  directory every prompt).

## 7a. Two things that only showed up in use (same day, fixed)

**`cliamp completion fish` is unusable.** It emits a non-empty, fully-formed
script in which every literal `%` has been eaten as a Go format verb — the
urfave/cli fish template is run through `fmt` a second time:

```fish
function __%!_(string=cliamp)perform_completion
printf "%!s(MISSING)\t%!s(MISSING)\n" "$parts[1]" "$parts[2]"
complete -c %! (string=cliamp)-f -a '(__%!_(string=cliamp)perform_completion)'
```

fish sources `~/.config/fish/completions` on every prompt, so installing that
printed a syntax error in front of every command typed. Not repairable by
substitution — the corruption is throughout, not in one token.

The **binary** is fine; only the wrapper is broken.
`cliamp --generate-shell-completion` is the real protocol and walks the whole
subcommand tree, so the completion is now hand-written around it
(`home/dot_config/fish/completions/cliamp.fish`) and stays dynamic. It drops
upstream's `-f` deliberately: cliamp's main argument is a path, and `-f` turns
file completion off entirely.

`run_after_23` now validates every generated completion with **`fish -n`**
(parse-only — it never sources the file) and installs nothing that fails,
leaving the previous one in place. `[ -s ]` waved this through; a completion
is code the shell runs on every prompt and "non-empty" is not a quality bar.

**The config dir must be chezmoi `private_`.** cliamp chmods
`~/.config/cliamp` to 0700 itself (it holds credentials). Chezmoi's source
state implied 0755, so it saw the mode drift, asked "has changed since chezmoi
last wrote it?", found no TTY, and **aborted the apply mid-run** — everything
ordered after it silently never happened. The source directory is
`home/dot_config/private_cliamp/`, which makes chezmoi expect 0700 and agree.
Worth remembering generally: a managed file inside a directory the app owns
means the *directory's* mode is part of the contract too.

## 8. Not done, on purpose

- **`contrib/quickshell/` — cliamp's own now-playing card.** A 300×72 Winamp-2
  spectrum panel driven by its `visstream` IPC. It reads omarchy's
  `colors.toml`, and adding a media card back to the bar is the opposite of the
  ask that removed ours.
- **Spotify / YouTube Music sign-in.** Both need an interactive OAuth flow that
  cannot be scripted. The config blocks and the reasoning are seeded; `cliamp
  setup` is the one manual step. YouTube Music needs nothing — cliamp ships
  fallback credentials and yt-dlp resolves YouTube anonymously here (measured
  today), so `cookies_from` stays commented until bot-detection starts biting.
